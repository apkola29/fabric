# Toolchain: the pinned skills and MCP servers behind every job

Every session and every job of the factory starts from the same pinned set of agent skills and MCP servers for Fabric, Power BI and Azure. This folder says which ones, `scripts/toolchain.py` checks, installs, verifies and updates them, and the lock file records exactly what was reviewed. Nothing is loaded that this folder does not name, and nothing is installed at run time (hard rule HR-9).

## Start from scratch

1. **Install the basics.** You need Git 2.32 or newer, Python 3.10 or newer, Node.js 22 or newer (the Fabric, Power BI and Azure MCP servers are npm packages, and the Fabric server asks for Node.js 22), and one host: GitHub Copilot CLI, Visual Studio Code with GitHub Copilot, or Claude Code. Optional: the GitHub CLI, the Azure CLI, .NET 10 (Bicep server), `uv` (Real-Time Intelligence server) and the Fabric CLI (`fab`, from the `ms-fabric-cli` package).
2. **Clone and look.** Clone the repository, open the `fabric-automation` folder, and run `python scripts/toolchain.py doctor`. It lists what is missing and what each missing piece is for.
3. **Install.** Run `python scripts/toolchain.py install` to see the plan, then `python scripts/toolchain.py install --apply`. It fetches the pinned skills, checks their digests, and copies them where Copilot CLI and VS Code look for them, inside this folder and not in your home folder: `.github/skills` (the 56 pinned skills and the two skills of this repository, 58 in all) and `.github/common` (the shared files that many skills link to as `../../common/`). It also writes the MCP files for those hosts. Claude Code gets `.claude/skills`, `.claude/common` and `.mcp.json` only when you ask for it with `--host claude-code`, because Copilot CLI reads `.mcp.json` before `.github/mcp.json`. Run it again any time: a second run changes nothing. It never replaces a folder it did not install, and it stops on a skill that you edited after it was installed, unless you pass `--force`.
4. **Sign in.** Run `az login` for the servers that use an Azure identity. The servers that sign in interactively (the hosted ones, and the `interactive` variant of the Power BI authoring server) open a browser sign-in on first use. The `service-readonly` variant of the Power BI authoring server signs in as a service principal, from variables that you set. The Power BI authoring server also asks you to accept its license: you do that once, yourself, and never through the agent (see Cautions).
5. **Verify.** Run `python scripts/toolchain.py verify --live` (add `--host claude-code` for Claude Code). It exits 0 only when the manifest, the profiles, the lock and the generated host files agree and what is installed for each host is what the lock pins. On a fresh clone it fails until step 3 has run. `verify` alone checks everything but what is installed.
6. **Work.** Start your host inside the `fabric-automation` folder or a folder below it (Copilot CLI reads the project's MCP files from the folder it starts in and the folders above it, up to the repository root, so starting at the repository root does not find them; VS Code reads `.vscode/mcp.json` of the folder it opens). The first time, Copilot CLI asks you to trust the folder and Claude Code asks you to approve each project server: until you do, the project servers do not appear. `AGENTS.md` and the `factory-router` skill route Fabric, Power BI and Azure tasks to the owning skill and MCP server of the profile in use (the default is `dev-factory`).

| Tool | Windows | macOS | Linux |
|---|---|---|---|
| Git | `winget install Git.Git` | `brew install git` | your package manager |
| Python 3.10+ | `winget install Python.Python.3.12` | `brew install python` | your package manager |
| Node.js 22+ | `winget install OpenJS.NodeJS.LTS` | `brew install node` | your package manager |
| Azure CLI | `winget install Microsoft.AzureCLI` | `brew install azure-cli` | the Microsoft package feed |
| GitHub Copilot CLI | `winget install GitHub.Copilot` | `brew install copilot-cli` | `npm install -g @github/copilot` |

## What gets loaded

A **mode** says who is working and what that may use. A **profile** is the exact list of skills and MCP server variants for one kind of session or job. A **variant** is one way of launching a server (its switches), with four declared facts: its credentials, its network, its access and whether it can run unattended.

| Mode | Who | May use | Used by |
|---|---|---|---|
| `dev` | A person, signed in as themselves | Anything, including the hosted servers and writes | Interactive sessions on a sandbox workspace |
| `agent` | The untrusted agent plane (design K4) | Only variants with no credentials, no network and read-only access | The planner, test author, implementer and verifiers (design 3.4) |
| `executor` | The trusted plane (K6, K7, K10) | Read-only variants that a workload identity can use, with no person involved | The static gates and the sandbox read-back (design 3.9, 3.10) |

`verify` refuses a profile that breaks the rules of its mode, so the credential-free agent plane cannot be handed a server that needs a sign-in. Every write in the agent and executor planes is a typed executor operation, not an MCP call.

| Profile | Mode | Loads |
|---|---|---|
| `agent-intake`, `agent-verifier` | agent | Nothing, on purpose |
| `agent-planner`, `agent-test-author` | agent | The semantic model and report skills, and the offline Fabric documentation |
| `agent-implementer` | agent | The same, plus the Power BI authoring server in read-only mode on local files |
| `executor-static-gates` | executor | The read-only authoring server on local files and the offline documentation |
| `executor-sandbox-read` | executor | The Fabric server (read-only tools) and the authoring server as a service principal |
| `dev-docs` | dev | Offline Fabric documentation and Microsoft Learn |
| `dev-fabric` | dev | All Fabric and Power BI skills and the Fabric servers |
| `dev-powerbi`, `dev-powerbi-hosted` | dev | Power BI authoring with the local or the hosted server, and Fabric IQ |
| `dev-realtime` | dev | Eventhouse, Eventstreams, Activator |
| `dev-azure` | dev | The Azure skills, the Azure and Bicep servers |
| `dev-factory` | dev | Everything needed to build and review the factory. The project MCP files are rendered from it |

`python scripts/toolchain.py list` shows the same table from the data, and `list --profile NAME` shows one profile with the version, access and credentials of every server.

## How it is pinned

| File | What it is | Edited by |
|---|---|---|
| `toolchain/toolchain.json` | The manifest: the modes, the hosts, the tools to check for, the two skill sources, the quarantine list and the MCP servers with their variants | A person |
| `toolchain/profiles.json` | The profiles: for each role the skills, the MCP server variants and the pinned command-line tools it loads | A person |
| `toolchain/toolchain.lock.json` | The lock: for each skill source the commit, for every skill a content digest, for each shared folder its digest; for each package the exact version and its integrity hash; for each launchable server variant its tool list with a digest of every tool schema, a digest of how it was launched and the day it was captured | `python scripts/toolchain.py lock` or `update --write`, reviewed in a pull request |
| `toolchain/instructions/factory-preamble.md` | The rules that every session and job loads | A person |
| `AGENTS.md`, `CLAUDE.md`, `GEMINI.md` (in the folder above this one) | The instructions of a session: `AGENTS.md` is the one copy, and `CLAUDE.md` and `GEMINI.md` only import it | A person |
| `toolchain/skills/factory-router/`, `toolchain/skills/factory-standards/` | The two skills this repository owns. The router sends work to the owning skill and server. The standards skill holds the Well-Architected, security and governance, lifecycle and architecture checks, each with its source and date | A person |
| `.github/mcp.json`, `.vscode/mcp.json` | The MCP files for Copilot CLI and VS Code, rendered from the default profile | `render --write-project` |
| `.github/skills`, `.github/common`, `.claude/skills`, `.claude/common`, `.mcp.json`, `.factory/` | What `install` and `fetch` generate for a machine: the skills, the shared folder, the Claude Code file and the local pack. Git ignores them and they are never published | `install`, `fetch` |

The lock has no `latest` and no range. A skill is identified by the commit of its upstream repository and by a digest of its files (line endings normalised, so the digest is the same on Windows and Linux), which `install` checks before it copies anything. The two skill sources are Microsoft's own: `microsoft/skills-for-fabric` and `microsoft/azure-skills`. The kit takes their skills only, and one more thing: 24 of the 26 Fabric skills tell the agent to read files in the plugin's `common` folder (`../../common/COMMON-CLI.md` and others, 627 references), which sits outside every skill folder, so the manifest names that folder as shared, the lock records its digest and `install` puts it beside the skills. Their plugins also bundle MCP servers, but at unpinned versions and with names that collide, so the manifest defines its own servers instead. A skill on the quarantine list (today `fabriciq-ontology-cli`, which authors a retiring format) is never loaded, even when a profile selects every skill of a plugin.

An MCP server that the kit can launch is captured once: the lock records its tool names and a digest of every tool schema, a digest of how it was launched (the command, the arguments with the exact package version, and the declared environment) and the day of the capture. A contract is kept only while the package version and the launch both match what was captured: change the launch line in the manifest and the old contract is dropped until it is captured again, and `verify` fails when a profile uses a contract that was captured for another launch. `verify --contracts` launches the server again and fails when a tool is added, removed or changed, which is how a job notices that an upstream server changed under it (HR-12). It also tells npm and uv not to take a version that was published after the day of the capture (`npm_config_before` and `UV_EXCLUDE_NEWER`), so that a dependency released later is not what gets checked. A server that is launched gets only the variables that its variant declares and the few that every process needs (its path and home folder, the proxy and certificate settings, and a fixed set of npm settings), never the rest of the shell's environment. Hosted servers cannot be captured without a sign-in, so they are not pinned this way, and they are for people only.

## What `verify` checks

`python scripts/toolchain.py verify` prints one line per finding, tagged with the check that raised it. It exits 1 on any `FAIL` (and with `--strict` on a `WARN`).

| Check | What it holds to account |
|---|---|
| V1 | `toolchain.json` and `profiles.json` follow the schema: no unknown key, no bad value, every variant states its four facts |
| V2 | Each profile obeys the rules of its mode and names only skills and servers that exist, and no quarantined skill by name |
| V3 | The lock exists, is fresh (its inputs digest, which covers the launches and the policy, matches the manifest), agrees with the manifest on the repository, path and tag of each source, and covers every source, plugin, shared folder, package and contract that a profile uses, and the package of every command-line tool that it pins. An unresolved package is a warning in `dev` and a failure in `agent` and `executor` |
| V4 | Every server that a profile uses has an exact launch line, never `latest`, and a profile of an `agent` or `executor` mode launches only through `npx` or `uvx`, the two launchers that have an offline form |
| V5 | `.github/mcp.json` and `.vscode/mcp.json` equal the rendering of the default profile |
| V6 | Every instructions file that a profile names exists |
| V7 | The quarantine list still names skills that exist (a warning when it does not) |
| V8 | Skill lint findings (a failure in `agent` mode, and for the skills of this repository in every mode: `render`, `install` and `fetch` stop on them too) and install steps that are inert in `agent` mode (a warning). The lint reads every text file of a skill, and a link counts as a file that holds its target |
| V9 | With `--live`: the skills, the shared folder and the MCP files installed for each host match the lock and the profile (the marker's profile, every needed skill present and unmodified, nothing left over). The files of the project are compared for every profile; those of the user (`$HOME/.copilot/...`) only for a `dev` profile, because `install` never writes them for an `agent` or `executor` profile, so there is nothing there that the kit could put right. No `.mcp.json` hides the rendering from Copilot CLI, and each command-line tool that the profile pins is at its pinned version (a failure for an `agent` or `executor` profile, a warning for a person) |
| V10 | A server of an `agent` or `executor` profile whose contract is skipped or unavailable is a warning, and the load plan of that profile is refused. A captured contract that was captured for another launch than the manifest's is a failure in every mode. With `--contracts`: every captured server is launched again and its tools must equal the lock, except one whose contract was captured for another launch (it is not launched; the failure above stands) |
| V11 | A captured contract lists at least one tool; `verify` reports it, and every command that resolves a profile (`render`, `install`, `fetch` and the load plan) stops on it |
| V12 | No server of a profile has the name of a server that a locked upstream plugin bundles. A host lets the plugin's server replace a project server of the same name, so the pinned server would be swapped for an unpinned one (seen with Copilot CLI 1.0.102) |
| V13 | A variant marked `tools_read_only` has only tools annotated read-only in its locked contract. Today that is the Fabric server's `docs` and `read` variants |
| V14 | When `toolchain/catalog.json` exists: it is well formed, it agrees with the manifest and the lock (the pinned servers, their documentation, the contracts that it takes its tool lists from, the tools that it flags or marks as knowledge), and the generated blocks of `AGENTS.md` and `toolchain/skills/factory-router/references/mcp-servers.md` are exactly what `python scripts/toolchain.py instructions --write` would write |

## How a job uses it

The runner picks a profile for the job and asks for its **load plan**: `python scripts/toolchain.py render --profile agent-implementer --host load-plan`. The plan lists each skill with its commit and digest, the skills of this repository (the router and the standards) and the shared folder with theirs, each server with its exact launch command and tool contract, the pinned command-line tools of the profile (`fab`, `powerbi-report-author`) with their exact version and hash, and the instruction files with their digests. The loader (K9) fetches the pinned pack into an image or a work folder with `fetch`, installs the pinned tools, checks the digests, and starts the agent with exactly that. Two rules make the plan safe to hand to a job. A plan for an `agent` or `executor` profile is refused unless every server it launches has a captured contract, because a contract that was never captured cannot be checked for drift. And its launches are `npx` or `uvx` only, and carry `--offline` and say `provisioning: preinstalled` (a launch that is not offline never says it): the loader has to install the exact version and integrity that the lock names into its image first, because `npx` and `uvx` check a download against the registry's own hash and not against the one in the lock. `verify` runs before the job and a failure is a stop. The same plan feeds the other hosts: `render --host copilot-cli|vscode|claude-code` prints their MCP files. `install` is for people: it refuses `--scope user` for an `agent` or `executor` profile, because a user-level file is shared by everything that user runs. A profile that lists no skill and no server (the intake parser and the verifier) gets neither skill of this repository: it works from the preamble alone.

## Instructions for agents

Four layers carry the instructions. Each is read at a different moment, so that the part that is always in context stays short.

| Layer | Where | Read | Holds |
|---|---|---|---|
| Session | `AGENTS.md` | by every host, at the start of a session in this folder | the rules that never bend, the steps of the start of a session, where knowledge comes from and the tools that give it, the tables of servers, the tools that are never called, the skills, the commands |
| Job | `toolchain/instructions/factory-preamble.md` | by every profile, through the load plan, on every run | the rules of a run: what you never do, what you have, where knowledge comes from, how to work, sign-in and reachability, freshness |
| Task | the `factory-router` skill | when a task starts | which skill and which server own the task, what to do when a server does not answer, and the reference of every server with its tools by kind (`references/mcp-servers.md`) |
| Reference | the `factory-standards` skill | when a change is planned or checked | the Well-Architected, security and governance, lifecycle and architecture checks, each with its source and date |

Which file each host reads:

| Host | Instruction file | Skills and MCP files | State |
|---|---|---|---|
| Copilot CLI | `AGENTS.md` (it also reads `CLAUDE.md` and `GEMINI.md`) | `.github/skills`, `.github/mcp.json` | the files it discovers were listed with `copilot instruction list` (version 1.0.102) |
| VS Code with Copilot | `AGENTS.md` | `.github/skills`, `.vscode/mcp.json` | documented, not run |
| Claude Code | `CLAUDE.md`, which imports `AGENTS.md`: Claude Code reads `AGENTS.md` on its own only from version 2.1.277 and only when none of `CLAUDE.md`, `.claude/CLAUDE.md` or `CLAUDE.local.md` is there | `.claude/skills` and `.mcp.json`, after `install --host claude-code`; it asks for approval of each project server (approve the ones that `list --profile NAME` shows) | the import is the documented way to share one file; run (version 2.1.162) only as far as listing the servers |
| Gemini CLI | `GEMINI.md`, which imports `AGENTS.md` | none rendered: take the launch lines of a profile from `python scripts/toolchain.py render --host load-plan --profile NAME` and add them to the Gemini settings by hand | documented, not run |
| Codex, Cursor and other tools that follow the AGENTS.md format | `AGENTS.md` | their own | not run |

`AGENTS.md` is the one copy. `CLAUDE.md` and `GEMINI.md` are three lines each (what the file is, a blank line and the import of `AGENTS.md`), and a test holds each to exactly that text, so that no second copy of the rules can grow there. The tables of servers, the table of tools that are never called, the tools that give knowledge and the skills in `AGENTS.md` are not typed: they sit between BEGIN GENERATED and END GENERATED comments and are written by `python scripts/toolchain.py instructions --write` from `toolchain/catalog.json`, the lock and the manifest, as is the reference `toolchain/skills/factory-router/references/mcp-servers.md`. A person read the catalog from the pages of Microsoft Learn (and the READMEs that they link): for each server where it runs, its release stage, what it needs, the pages with their dates, its tools by kind (read, write, destructive), the tools that give knowledge and the tools that no agent calls (those that change security, permissions, a connection, a schedule or a setting, accept a license or hand out a credential, each under its area of tier T3 or the rule that forbids it). The tool lists of the stdio servers are the lock's, as the servers reported them. `verify` fails (V14) when a generated file is not what the catalog says, and the fact list watches every page of the catalog and the tool names on it, so that a page that changed is a drift to read again and a catalog that is edited is checked by a model family other than the one that wrote it (rule 9). A job does not read these files: it gets the preamble from its profile. A test (`ReviewedTextTests`) holds the text of `AGENTS.md`, the preamble, the two skills of this repository, the catalog, the reference pack and this section of the README by a digest, so that no sentence can be added, changed or removed without a deliberate change of the digest: the change is checked by a model family other than the one that wrote it, the result is recorded under `docs/reviews`, and only then is the digest replaced by the one that the failure prints. The sources for each host are in `../docs/research/raw/t10-toolchain-grounding.md` (6b).

How an agent finds and uses knowledge, in this order: the requirement and the existing deployment (the folders of the workspace that is backed up in Git: read them first, follow their patterns, cite the files by path; two patterns that disagree, or a secret in a file, are raised and never copied); the owning skill and the MCP servers of the profile (documentation and specifications first, through the tools that the catalog marks as giving knowledge, live state second, changes last); the standards skill; and current documentation from the Learn and Azure servers, never memory. Sign-in belongs to the person or the runner: `az login` (or the service principal or workload identity of a job) for the servers that use an Azure identity, a browser sign-in for the servers that act as the person (the hosted ones, and the `interactive` variant of the Power BI authoring server). The agent checks that a server answers with one read-only call. When one does not, it carries on with what needs no sign-in (the Fabric documentation variant, Learn, Bicep, the offline authoring server, the skills, the repository and the standards), stops only the step that needed the missing server, and does not do the same live operation through another route or another identity. Before anything that changes a tenant it says the route, the identity and the change and waits for the person to approve that statement: the task is not the approval.

Freshness: every run looks and no run adopts. Before the work, the runner (or the agent, in a session) runs `python scripts/toolchain.py update --check --fail-on-update --summary-file .factory/update-summary.md` (the folder `.factory` is not published; it needs the network and takes under a minute, because the skill sources are fetched again each time). Exit 0 means that nothing newer was found, and the notes say what could not be checked: a package that "could not be resolved now" keeps its locked version and was not looked at, and the summary then says that part of the check did not run. Exit 3 means that the candidate lock differs from the lock: a skill or a package is newer upstream, or the manifest was edited, and the summary says which and what it would stop. The check reads metadata and launches no server, so it does not see a change in what a server's tools do: the weekly job launches the pinned servers and compares their tools with the lock (`verify --contracts`), and a capture of the newest versions is a manual step on a hosted runner (`update --contracts` or `lock --contracts`). Exit 1 or 2 means that the check did not finish (an unreachable source, an unreadable lock): the run reports the error and does not say that nothing is newer, and the command removes the summary of an earlier check before it starts, so that no old result is mistaken for this one (a command line that the parser refuses, exit 2, stops before that, so the summary file counts only after exit 0 or 3). In every case the run goes on with the pinned versions and carries the result in its pull request or its job summary: the summary after exit 0 or 3, the error line after exit 1 or 2. A job's agent does not run the command (the agent plane has no network and no copy of the script): the runner does, and gives the result. Taking a newer version is a separate pull request: `update --write` writes the lock only when every profile still verifies, and a person reviews it. The reason is the same as for the pin: a skill or a server that nobody reviewed would run with the privileges of the job, and a skill text is an instruction to an agent. The session start also reads the Fabric MCP directory through the Learn server, where there is one, and reports a server that `AGENTS.md` lists in none of its tables.

## Keeping it current

- A weekly job (the `toolchain` job of the fact-check workflow) runs `update --check`, resolves a candidate lock on a GitHub-hosted runner, and keeps it as an artifact. It changes nothing in the repository. It also launches the pinned servers again (`verify --contracts`), bounded by the day of each capture as described above.
- The weekly fact check also reads the pages of `toolchain/catalog.json`: the update date of each page of Learn, the tool names and the release stage on the pages that list them, and the READMEs that name the flagged tools. A page that changed is a drift and no failure: a person reads it again, edits the catalog, runs `python scripts/toolchain.py instructions --write`, and the change is checked by a model family other than the one that wrote it.
- `python scripts/toolchain.py update` prints the gap analysis: new, removed, renamed and changed skills, new package versions, changed tool contracts, and which profile would stop verifying because of it. A renamed skill is the typical case: release v0.3.20 renamed one.
- `python scripts/toolchain.py update --write` writes the new lock only when every profile still verifies. Review it as a pull request, run `fetch` and `install`, and merge. To roll back, revert the lock.
- A lock refresh belongs on a hosted runner. On a network that blocks the npm or NuGet registry, a local `lock` leaves those packages `unresolved` and says so. Such a lock fails `verify` (V3) for every `agent` and `executor` profile that launches the package, and `fetch` without `--profile` stops on the first of those profiles for the same reason, as every command that resolves a profile does. `fetch --profile dev-factory` still fetches the skills for a person: a `dev` profile only warns, and leaves the server out of its rendering.

## Add a skill source, a server or a profile

1. Edit `toolchain/toolchain.json` or `toolchain/profiles.json`. Give a new variant its four facts honestly: a variant that needs a sign-in has credentials other than `none`, and a variant that can write has access `read-write`. If the variant's read-only switch removes the writing tools from the server's list, add `"tools_read_only": true` and the lock has to show it (V13). Choose a server id that no upstream plugin uses (V12).
2. Run `python scripts/toolchain.py lock`, then `python scripts/toolchain.py verify`.
3. Add or change the entry of the server in `toolchain/catalog.json`, read from its Learn page: where it runs, its stage, what it needs, the pages, its tools by kind (a stdio server takes them from its lock contract), the tools that give knowledge and the tools that no agent calls. Run `python scripts/toolchain.py instructions --write`, and add a fact-list claim for each new page (`scripts/facts.json`). `verify` fails (V14) until the generated files are what the catalog says.
4. If the default profile changed, run `python scripts/toolchain.py render --write-project`.
5. Run the tests: `python -m unittest discover -s scripts -p "test_*.py"`.

## Cautions

- **License acceptance.** The Power BI authoring server blocks every tool until its license is accepted. The kit never accepts it, and neither does an agent: the operator reads the license and accepts it, once, on purpose, by setting the environment variable that the manifest names (`PBI_MODELING_MCP_ACCEPT_EULA`) to `true` in the operator's own shell before the host starts, or by the server's own flag. The rendered files pass that variable through with the default `false`. The server also offers an `accept_eula` tool that an agent can call when a person tells it to; the instructions of this kit forbid that (AGENTS.md, rule 3): accepting is the operator's own act.
- **Hosted servers act as you.** The hosted Fabric, Fabric IQ, SQL endpoint and Power BI authoring servers use your browser sign-in; the sign-in method of the hosted Azure cost server is not documented, and the kit treats it the same way. Fabric IQ does not support service principals. Use them on a sandbox workspace and only in the `dev` mode.
- **The rules here are stricter than some pinned skills.** A few upstream skills tell the agent to install a tool (`winget install`, `pip install`, `npm install -g`) or to fall back to another route when their MCP tool is missing, without asking. The preamble overrides that: nothing is installed by an agent, and a missing tool is reported and asked about first. `doctor` shows what a machine lacks and what each piece is for, and a person installs it; `install` places the pinned skills and MCP files, not tools.
- **Two copies of the same thing.** Your own configuration may already define Fabric or Power BI servers (the user file `$HOME/.copilot/mcp-config.json`, a VS Code profile), or you may have installed the upstream plugins, whose bundles register their own skills and unpinned servers. A session then sees two sets. The kit does not touch your files. See what is active with `copilot mcp list` and `copilot plugin list`, and switch the extra ones off for this project with `copilot mcp disable NAME` or `copilot plugin disable NAME`. A factory job is meant to start from the pack that `fetch` writes and from nothing else (K9), so this concerns people's sessions.
- **Unattended identity is not proven.** Whether each server accepts a service principal or a workload identity is a Phase 0 spike (S2, S6). The manifest marks what the documentation says, and `verify` only lets a variant into the executor plane when it says `true`.
- **No secrets, no tenant data.** The files in this folder are public. They hold server addresses, package names and digests, never a token, a tenant, a workspace or an item identifier.
- **Contract drift is a stop.** A missing, renamed or changed tool is reported, not worked around.

## Limits

- Nothing here has been run against a tenant. The pinned servers and skills are real and were read and launched, but no job has used them against Fabric.
- The lock records a tool contract only for a server that was launched. Six of the 15 are captured, on a hosted runner because `npx` cannot fetch a package on the machine where the kit was built: the three variants of the Fabric server at the pinned 1.6.0 (6, 34 and 62 tools), the read variant of the Azure server (70 tools), the Real-Time Intelligence server (39 tools) and the Bicep server at the pinned 0.48.1 (14 tools; its first launch line used `dnx`, which is not on the runner's path, and the line that goes through `dotnet tool exec` was captured on 2026-11-01). The Power BI authoring variants are skipped because their license is accepted by a person, and hosted servers are never captured because they need a sign-in. So the load plan of `agent-implementer`, `executor-static-gates` and `executor-sandbox-read`, which use the Power BI authoring server, is refused until an operator who accepted the license captures it. The weekly job of the fact-check workflow reads registry and tag metadata and re-checks the pinned contracts; it never launches a server version that nobody has reviewed. A person who wants a new capture dispatches that workflow with its `capture` input, reviews the candidate lock that it keeps as an artifact, and commits it.
- The tool annotations in a contract are the server's own claim. V13 holds a variant to them, but it cannot prove that a switch blocks a write. The Fabric server's read-only switch removes the writing tools from its list (all 34 tools that remain are annotated read-only), so its `docs` and `read` variants carry `tools_read_only`. The Azure server's list under `--read-only` has 70 tools of which only 5 are annotated read-only, because it groups commands under one tool per service and blocks the writes inside; the Power BI authoring server's `--readonly` also works inside the server. Those variants make no `tools_read_only` promise, and their read-only access rests on the documented switch.
- The Power BI authoring server blocks every tool until its license is accepted, and the kit never accepts it. Its contract stays `skipped` until an operator who accepted it runs the capture.
- Copilot CLI (version 1.0.102) was run against the generated files: it listed all 8 project servers of `dev-factory` and the 57 project skills that existed then (the standards skill made it 58 later, and the count was not taken again), and a project skill won over a plugin skill of the same name. Claude Code (version 2.1.162) was run only as far as listing the two servers of a generated `.mcp.json`, which it showed as pending approval; no server was started. VS Code was not run, and receives files in its documented format. The first run on Linux is the hosted runner's.
- The MCP probe asks `server/discover` first, as the 2026-07-28 revision describes, and falls back to the older `initialize` handshake on a new process when nothing has answered after 20 seconds (a slow start is not a legacy server: with a wait of 5 seconds the real local Fabric server, which took 4.6 seconds to answer on a loaded machine, was recorded as a legacy server in three runs out of four). On the hosted runner the Fabric server (1.6.0) and the Azure server (4.0.0-beta.4) answered `server/discover`, so their four contracts record the era `modern` (with the same tools that the older handshake gave); the real local Fabric server (1.5.0) answers both eras on a developer machine, and the Real-Time Intelligence server answers only the older handshake. A server that answers only the new era was never available, so that path is tested against a stand-in. A server that accepts `initialize` but names a revision that the probe does not speak (a future date, an impossible one) is not captured: the probe leaves it before it asks for the tools, as the lifecycle page of the specification asks of a client.
- Five links in the pinned skills point at folders that do not exist at the pinned tag (`mcp-setup` four times and `spark-authoring-cli` once). They are broken upstream and the kit does not rewrite upstream files.
- The SQL endpoint server's one tool is called `execute_query` by the skill and the plugin and `executeSQL` by Microsoft Learn. Which is current needs a signed-in session, so it is not settled here; the router tells the agent to use the name that the loaded server lists.
- `gh-aw` and the Copilot cloud agent have no renderer yet. The load plan is the interface for them. gh-aw resolves `skills:` entries to commits itself, so a renderer is a thin step.
- Dependencies are not locked by hash. The three npm servers (Fabric, Azure, Power BI authoring) declare no dependency but optional platform packages at their own exact version, so their pin fixes what runs. The Real-Time Intelligence server and the two pinned command-line tools (`fab` and `powerbi-report-author`) declare version ranges for their dependencies, so what they pull in is decided on the day they are installed. The weekly check bounds that for the servers it launches (`verify --contracts` sets the day after the capture as the limit, so the Real-Time Intelligence server resolves nothing that was published later). It does not install the two command-line tools, so their dependencies have no bound at all. A bound by the day of the capture keeps out a release that came later but not a dependency that already existed and that nobody reviewed. A job that must not depend on that installs these tools into its image from a hash-locked environment, which the loader has to provide: the kit pins the tools by version and integrity, not their dependencies. The NuGet package of the Bicep server was not examined for this.
- A candidate lock from a manual capture is the output of a run that executes package versions nobody has reviewed, and such a package could forge the artifact. Read its diff against the lock, as for any pull request, before committing it. Nothing promotes it automatically.
- A sync client (OneDrive), a virus scanner or the indexer can hold a folder that was just written open for a moment, and Windows then refuses to move it. The kit waits for that, up to about six seconds, and otherwise stops with an error line; running `install --apply` again finishes the job, because a skill folder that holds exactly the pinned content is taken as it is, even when no marker names it. A folder with any other content stays a conflict.
- The cache of the pack (`.factory/pack/.cache`) is local state, and the kit never trusts what is in it: whenever it needs a commit it removes the cache folder of that commit (a link at the folder is refused, and a link inside it is not followed) and fetches into a new one. A configuration, a `commondir` file, a hook, an alternates file or a link that someone placed there is therefore never read. Git runs from an empty folder that is also its home folder, with no configuration of the operator or of the system and without a credential helper, a `.netrc`, the `NETRC` variable or a client certificate from the environment, so an anonymous call sends no credential. What the operator sets on purpose to change how Git trusts a server or reaches it (a CA file, `GIT_SSL_NO_VERIFY`, a proxy) is honoured, and that includes a credential in the address of a proxy: it goes to that proxy, as it does for any program, and to no repository (a test with a loopback proxy and made-up credentials saw Git send them once the operator also set `GIT_HTTP_PROXY_AUTHMETHOD=basic`). The call is anonymous towards the repository, and not towards an authenticating proxy that the operator configured. The probe of an MCP server, which runs code that nobody has reviewed, gets such an address without the credential. The anonymous calls also tell Git not to answer a Negotiate challenge with empty credentials (`http.emptyAuth=false`), because on Windows that is how the credentials of the logon session could be offered to a server; this was measured on the author's machine (Git 2.56.0 for Windows against a loopback server, which made no token) and the exposure was not reproduced there, so the setting is a precaution that is UNVERIFIED on a domain-joined machine.
- The Bicep server launches through `dotnet tool exec PACKAGE@VERSION --yes`, and a hosted run launched that line against the real package (0.48.1) on 2026-11-01: the server answered `server/discover` with the revision 2026-07-28 and listed 14 tools, and its contract is in the lock. It names itself `Azure.Bicep.McpServer` with a version of four parts (its assembly version, which is not the package's); the probe's filter replaces a name that looks like a host name and a version that looks like an address by `unknown`, so the contract records both so and identifies the server by the package version and the schema digest of each tool. NuGet's own launch template and Microsoft Learn use the `dnx` script instead; the kit does not, because the script sits in the SDK folder, which is not on the path of every installation (the hosted runner image has the SDK 10.0.403 and no `dnx` on its path), while `dotnet` is the one command that `doctor` already checks. Learn lists `--yes` as available from .NET 11, and the help text of the 10.0.403 SDK does not list it. It was tried there (on Windows, with a small tool package from a local feed, so that no network was needed): after the package or before it, to `dotnet tool exec` or to `dnx`, the SDK takes `--yes` and the tool receives no argument, whereas an invented option after the package is handed to the tool. A first launch without `--yes` did not wait for an answer when the input was redirected. On the first use of the SDK by a user the .NET CLI also writes a banner and a telemetry notice to the error stream (not to the output stream, so the protocol is not disturbed), collects usage telemetry (the notice says so) and generates a development certificate; the manifest declares `DOTNET_NOLOGO`, `DOTNET_CLI_TELEMETRY_OPTOUT`, `DOTNET_SKIP_FIRST_TIME_EXPERIENCE` and `DOTNET_GENERATE_ASPNET_CERTIFICATE` for the server, which silenced the banner and skipped the certificate in a test with a fresh `DOTNET_CLI_HOME` (the folder that the SDK keeps its first-use state in; on Windows a fresh HOME or USERPROFILE does not move it, and a reviewer who tried that saw nothing), and an operator's own value of any of them wins. The server is in no agent or executor profile, so a change of its tools cannot stop a job, and `dotnet` has no offline form; the weekly check launches it with the other captured servers.
- A variable that the manifest declares with a default reaches Copilot CLI and Claude Code as `${NAME:-default}`, the load plan as a pair of the variable and its default, and the probe as the operator's value or else the default. The VS Code format has `${env:NAME}` and no default (the capability table of the VS Code MCP reference, read 2026-11-01, lists `${NAME:-default}` only for the portable `.mcp.json` formats), so the kit writes `${env:NAME}` for VS Code, and a variable that the environment of VS Code does not hold has no default there; what VS Code passes for an unset variable is not documented, and VS Code was not run. For the four `DOTNET_*` variables of the Bicep server that means the first-use experience of the .NET CLI is switched off only if they are set where VS Code starts; unset, it runs once per user and writes to the error stream, and the protocol is not disturbed. A literal default for VS Code would take away the way an operator accepts the Power BI license (`PBI_MODELING_MCP_ACCEPT_EULA` is declared with the default `false`), so the kit does not write one.
- Instruction files: Copilot CLI reads `AGENTS.md`, `CLAUDE.md` and `GEMINI.md` and expands the `@AGENTS.md` import of `CLAUDE.md`, so the text of `AGENTS.md` may reach the model twice. Its page says that it removes duplicate copies of identical files and gives no rule for an imported copy; whether it does here could not be read, and `AGENTS.md` is kept short for that reason (a test holds it to 100 lines). Claude Code reads `AGENTS.md` on its own only from version 2.1.277, and not when a `CLAUDE.md`, a `.claude/CLAUDE.md` or a `CLAUDE.local.md` is there; the author's machine has 2.1.162, so `CLAUDE.md` imports it; that import is what makes the one copy reach Claude Code, and it was not run against a model. Gemini CLI, Codex and Cursor were not run, and neither was VS Code.
- The publish script (`scripts/sync_to_github.ps1`) is PowerShell and uses `robocopy`, so it runs on Windows only. The hosted workflows run the validator and the tests on Linux. The commands in the instruction files say `python`: on a system where that name is not found, use `python3`.
- Inside a folder that OneDrive or an antivirus keeps scanning, `install --apply` can stop with "Access is denied" while the other program holds a file that was just written (seen once, in a scratch copy of this project, after the retry window of about six seconds). The error is an error line and not a half state that `verify --live` hides: `verify --live` reports that the managed marker is missing. Run `install --apply` again; it is idempotent. If it keeps failing, install outside the synced folder. UNVERIFIED: that a second run always completes.
- The agent plane has no network and no sign-in. A hosted server needs one, and the Learn server needs the internet, so a job of the `agent` or `executor` mode reaches none of them: its knowledge is the repository, the pinned skills, the offline Fabric documentation and the standards. "The agent signs in" holds for a person's session. Whether a service principal or a workload identity can use each hosted server is the Phase 0 spike (S2, S6).
- The check before each job is the runner's step (design 3.13), and the runner is part of the factory runtime, which is not built. Today the check runs in a person's session (step 4 of `AGENTS.md`) and once a week in the fact-check workflow, which also reads the Fabric MCP server directory page through the fact list (a renamed or removed server, or a later update date, shows as drift). A run that finds something newer reports it and does not adopt it. That is a decision of the design (a pin that nobody reviews is not a pin), and the owner can change it.
- Only two skill sources are in scope. The bundled custom agents of the Fabric plugin (FabricAdmin and others) are not loaded.
