# Verification material

The process material behind the evidence in [docs/reviews](../docs/reviews/README.md): the briefs that the reviewers and the implementers were given, what the implementers reported, and the scripts that produced the mutation, replay, Linux and fresh-clone numbers. It is kept so that a reader can see how the checks were done and can run them again. It is **not** part of the [toolchain kit](../toolchain/README.md), and nothing in the kit depends on it.

## How the pieces were used

**A review.** The reviewer gets the shared preamble, then the brief of its slice. It works in its own clean clone of the public repository at a given commit, reads the delta, tries to break the fixes, mutates the safeguards of its slice and answers with findings that each carry a reproduction or a primary-source citation (UNVERIFIED where it could not reproduce), capped in number and length. The author then checks every point against the code or the source before accepting or rejecting it. The replies are in `docs/reviews`, the author's checks in the findings file of each round.

**A mutation proof.** A specification names the project, the tests that should notice, and a list of mutations (a file, the old text, the new text). The harness copies the project once, checks that the tests pass, and for each mutation requires the old text to occur exactly once, writes the broken text, runs the tests and puts the file back. A mutation that no test notices is reported as SURVIVED and is a gap in the tests.

```
python verification/tools/mutation_specs_fourth_look.py --out %TEMP%
python verification/tools/mutate.py %TEMP%/mutations-fourth-look-a.json
```

The 123 mutations of the instruction layer are run the same way, one JSON file for each set (`mutations-instruction-layer.json`, `mutations-standards-pack.json`, `mutations-update-summary.json`, `mutations-closure-review.json`, `mutations-third-look.json` and `mutations-fourth-look.json`), from `python verification/tools/mutation_specs_instruction_layer.py --out %TEMP%`. A mutation of this set changes one text of an instruction file, of the fact list, of a reference file or of the update command, and the tests that are meant to notice it are the ones of the instruction layer, the reference pack or the update report. The last set also runs `ReviewedTextTests`, which holds the text of the instruction files and of the reference pack by a digest and so kills every change of that text: it is left out of the other sets, because it would hide what their tests hold.

**The checks of the reference pack.** The programs that read the pack take the folder of the nine reference files (`toolchain/skills/factory-standards/references`) and, except `pack_dates.py`, the pages reduced to text (44 pages for the nine files; the scratch folders of the reviews held the pages of the files that were being checked): one file for each page, named by the page address with every run of other characters replaced by a hyphen, and starting with a line `SOURCE: <address>`; `learn_extract.py OUTDIR URL...` writes them. `pack_mechanics.py PACKDIR SOURCEDIR` prints a line for every check whose citation, number or heading it cannot find in the cited pages, or that copies more than 12 words in a row. `pack_quotes.py PACKDIR SOURCEDIR REPORT...` reads a report with one row for each check (`id | verdict | quote | reason`) and prints the rows whose quote is not in the cited section of the cited page, which is the proof that the row was read against the page. `pack_dates.py PACKDIR` compares the date of each page in the pack with the live page (it needs the network and no sign-in). `pack_hedges.py PACKDIR SOURCEDIR [ID...]` prints, for each check, the sentences of the cited sections and the hedge words of those sentences that the check does not carry. None of them decides whether a line is supported; a reader does. The rows that close a finding (`P-F1`, `B-K2` and so on) are not read by `pack_quotes.py`: their quotes were looked up in the pack or in a page by a small scratch script that is not kept.

**The checks of the catalog.** `catalog_quotes.py check PROJECT SOURCEDIR REPORT...` reads a report with one row for each statement of the catalog (`<server>:use`, `<server>#3`, `<server>:flagged` and so on) and prints the rows whose quote is not on a page that the row's server cites, the quotes of more than 12 words and the quotes whose fragments are on different pages. `catalog_quotes.py lists PROJECT SOURCEDIR` compares the tools that the pages and READMEs list with the tools of the catalog, set by set, and exits 1 on a difference. The fact list (`scripts/facts.json`) keeps the claims behind the statements true every week; `scripts/test_verify_facts.py` holds, for each claim, a sample that passes and a change of the page that the claim must notice.

**The replay.** Each of the 51 scenarios copies the toolchain files of a tree into a scratch folder with its own home folder, applies the change that a reviewer described, runs the command line and says whether the behaviour that the reviewer reported still happens. REPRODUCED means that the defect is present. Run on the commit that the reviewers reviewed it reproduces the defects; run on the corrected tree none should reproduce.

```
python verification/tools/replay.py .                    # the tree of this folder
python verification/tools/replay.py OLD_TREE --only D1-1,D2-1
```

`OLD_TREE` is a checkout of an earlier commit (the folder that holds `scripts` and `toolchain`). A tree whose lock holds no captured contract borrows one from the lock of this project (`--reference-lock` names another).

**The Linux probe and the fresh-clone run.** `ci_probe.ps1` pushes the current files to a throw-away branch, dispatches the validate workflow there, prints the test count and deletes the branch; it needs a signed-in `gh` with the right to push and never touches the main branch. Run it with PowerShell 7 (`pwsh`): Windows PowerShell 5.1 stops at the first line that git writes to its error stream, which happens when the push prints a notice, and then the branch is left on GitHub. `fresh_clone_acceptance.ps1 -Sha COMMIT` clones the public repository at that commit into a temporary folder and runs the first-run checks with a scratch home folder.

## Limits

- These are scratch tools. They were written while the work was done, they are Windows-first (the PowerShell scripts need PowerShell, the Python ones run on both systems), the tests of this repository do not cover them, and no model family reviewed them as a whole: the families reviewed the kit. In the catalog rounds they also read `tools/catalog_quotes.py` (rounds 2 to 7) and the mutations of `tools/mutation_specs_catalog.py` that had been rewritten or added (rounds 6 and 7); none of them read the rest of this folder. Read the tools before you trust them.
- The replay scenarios and the mutation specifications are tied to the code of the commits that they were written for. When the code moves, a mutation reports ERROR because its old text no longer occurs exactly once, and a replay scenario may stop meaning what it meant. The acceptance script checks what the lock held when it was written.
- Not kept: the written specifications of the first two rounds of fixes (they were scratch files), the first build specification of the kit (a working document for the implementers, not for publication), the scripts of the SDK experiments (they used a small tool package that was not kept), the scratch scripts that built the review snapshots, copied the replies into the records and looked up the quotes of the closure rows, and the raw replies of the reviewers (the normalised replies are in `docs/reviews`). The pages that the reviewers read are not kept either: they change without notice, and the tools above say what format they need.
- The numbers in the records came from these tools run on the author's Windows machine and on the hosted Linux runner. The records say which.
