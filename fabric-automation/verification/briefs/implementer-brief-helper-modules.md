### Y-1 (reviewer D2-1 High, D2-3 Medium; the author rates them Medium and Low-Medium). An existing cache folder is trusted although it is not

`fetch_git` replaces `<cache>/config` and keeps a cache folder that already holds the commit. Two reproductions: (1) a `commondir` file in the cache folder that names another repository whose config has `remote.<file-url>.uploadpack` pointing at a program: the program ran during `fetch_git`, because Git read the configuration of the common directory, which we did not replace; (2) a junction (Windows) or symbolic link inside the cache (the `objects` folder replaced by a link to a folder outside the pack): `vendor_skills` succeeded and Git wrote 3 files into the outside folder. The README already admits that hooks and alternates in an existing cache are not neutralised; these two show that the class is wider than the list.
Decision: a cache folder is never reused. `fetch_git(url, commit, dest, runner)` first refuses a link at `dest` (as now), then, if anything exists at `dest` (`os.path.lexists`), removes it with the module's `_remove` (which must not follow a link inside it: prove that with a real junction or symbolic link inside the old cache, whose target must be left untouched, and with a link as the old `dest` itself, which is refused before anything), and then makes a fresh bare repository and fetches the commit, exactly as it does for a missing folder today. The "dest exists: reset the configuration, `_has_commit`, return dest" shortcut goes away. Keep `_reset_cache_config` after `git init` (cheap, and `git init` could take a template; `GIT_TEMPLATE_DIR` is dropped, but keep the belt) and remove the call before use if it becomes dead code. Update the docstring of `fetch_git` and the comments that describe reuse.
`vendor_skills` keeps calling `fetch_git` once per commit per call (its `fetched` dictionary), so one call to `vendor_skills` fetches each commit once. The other implementer changes `resolve_source` in `toolchain.py` so that the lock resolution calls `fetch_git` on every run too.
Tests: (a) the `commondir` reproduction (two bare repositories; the cache folder holds a `commondir` file; the common repository's config has an `uploadpack` setting that runs a harmless marker program; assert that the marker is NOT executed, the old `commondir` is gone and the result is correct; first show that plain git with the same environment does execute it, as the neighbouring hostile-repository tests do); (b) the real junction or symbolic link inside an old cache (`objects`): after `fetch_git` and after `vendor_skills` the outside folder is exactly as it was (same files, same bytes, no new file); (c) an old cache with a `hooks/reference-transaction` script (the author's earlier README named this a residual) does not run it; (d) `fetch_git` on an existing cache that holds the commit still fetches again (assert on the runner calls: init and fetch happen) and a cache that holds junk is removed; (e) the existing tests: those that relied on reuse change on purpose, say which and why. ### Y-2 (reviewer D2-2 High; the author rates it Medium). Anonymous Git reads `.netrc` and sends its credentials

Git inherits HOME and USERPROFILE, and libcurl (inside Git) reads `~/.netrc` (and `_netrc` on Windows), so a network call that is meant to be anonymous sends the stored credentials when a server answers 401. A `default` entry matches any host, so a manifest that names a hostile address would receive them. Reproduce with a loopback HTTPS server that answers 401 with a Basic challenge and records the `Authorization` header (the certificate: generate a throw-away CA and server certificate with the `openssl` command line where it exists, e.g. the `openssl` of Git for Windows under `...\Git\usr\bin` or the system one; skip the test when none can be found; make Git trust it by injecting `-c http.sslCAInfo=<ca.pem>` into the argv through a thin runner wrapper in the test, so that the isolation of the environment under test is the real one), with a synthetic `.netrc` and `_netrc` (login `u`, password `p`, `default` and a `machine` entry for the loopback address) in a scratch folder that the test sets as HOME and USERPROFILE of the test process (patch the environment narrowly).
Decision: every Git call that `_run_alone` makes gets HOME, USERPROFILE and XDG_CONFIG_HOME set to the new empty working folder that it already creates (do not remove the variable: with HOME unset, libcurl falls back to the passwd entry on POSIX and finds the real home). Also remove HOMEDRIVE and HOMEPATH from the child (they stay None in the overlay). Think about whether anything else in the process environment can name a credential file for Git or libcurl on either platform (look at what `_GIT_CONFIG_DROPPED`, `_GIT_REPOSITORY_DROPPED` and `_GIT_NETWORK_DROPPED` already drop; the `curl` and `SSL_CERT_*` families, `NETRC`) and say in the report what you checked and decided. Note that reading a local cache (`_run_bytes`) does not need it, but check that it does not break.
Tests: the real-process test above with a CONTROL (plain Git with the same environment and the same server DOES send the synthetic credentials, so the test is sensitive; then `resolve_git_ref` and `fetch_git` send none, and each of the two makes the request without an `Authorization` header); a unit test that the overlay and the working folder of the call are as specified (HOME, USERPROFILE and XDG_CONFIG_HOME name the empty folder that is also the working directory; the folder is empty and exists during the call and is gone after it); mutations: drop each of the three variables from the overlay (the real test must notice USERPROFILE on Windows and HOME elsewhere; say which mutations only one platform can notice).

### Y-3 (reviewer D2-4 Medium). A body-reading error erases an authoritative 404

`_stage_failure` looks at the error before the status, so a registry answer of 404 or 410 whose body could not be read (too large, for example) becomes `network`, which lets the npm CLI answer stand alone. Reproduce with the stand-in runner (the neighbours of `_resolve_npm` show how): `{"status": 404, "error": "too-large"}` from the registry and a valid CLI answer.
Decision: a received status of 404 or 410 wins over a body error: the answer is `notfound` (the same outcome as a clean 404), so the CLI answer is not accepted alone. Statuses 403, 429 and 5xx and a missing response keep the documented fallback to the CLI (read the comments and the neighbouring tests before you decide; do not change them). Make the message and the docstring say what is now true. Tests: 404 and 410 with each kind of body error that `_get` can report; the same with a clean body (existing); 403 and 5xx with a body error still reach the CLI-only path (existing behaviour, assert it). Mutations: restore the old order; treat only 404 (not 410) as authoritative.

### Y-4 (reviewer D2-5 Medium). A successful `initialize` that names a revision the probe does not speak is accepted

`_legacy` accepts any ASCII date as the protocol of a successful `initialize` answer and goes on to `tools/list`; a test explicitly accepts `2027-01-01`, and the capture recorded `protocol: 2027-01-01`. The specification says a client that does not support the version in the server's answer SHOULD disconnect.
Decision: after a successful `initialize`, the protocol version must be one of `HANDSHAKE_VERSIONS`; anything else (a future date, an impossible date, `MODERN_VERSION`) is `McpProbeError("protocol-error: unsupported protocol version")` and the session is closed without `notifications/initialized` or `tools/list`. The committed lock holds `fabric-rti-local/default` with protocol `2025-11-25` (legacy) and four modern contracts with `2026-07-28`: both stay valid (assert it in a test that reads the committed lock and checks that every captured legacy contract's protocol is in `HANDSHAKE_VERSIONS`, every modern one is `MODERN_VERSION`). Replace the test that accepts `2027-01-01` by tests that refuse it (a future date, `9999-99-99`, `2026-07-28`) and that show that no `tools/list` request was sent. Through the real composition (the stand-in server, `probe_stdio`, then `toolchain.capture_contract` is in the other implementer's file, so only go as far as `probe_stdio` and `capture_env`): nothing is recorded. Mutations: accept any date again; accept only the newest handshake revision; check membership after `notifications/initialized`.

### Y-5 (reviewer D2-6 Low, Windows only). Clearing the read-only attribute changes the protection of another name of the same file

On Windows `make_writable` clears the read-only attribute of a file, and the attribute belongs to the file, not to the name: when the cache's `config` is a hard link to an outside read-only file, replacing it left the outside file writable (0o444 became 0o666; its content was unchanged).
Decision: `make_writable(path)` does nothing for a file that has more than one name (`os.stat(path).st_nlink > 1`), also on Windows; the delete that follows then fails with the system's refusal, which surfaces as the existing errors (`cannot write the cache configuration`, a failed removal). It is a deliberate refusal: nothing the kit or Git writes has two names. Keep the current behaviour for `st_nlink == 1` and for a path that cannot be examined. Tests: a real hard link on a platform that can make one (on Windows: the outside file is still read-only after the failed replacement; the content is untouched; on POSIX the function is a no-op as before), and a mocked variant everywhere (patch `toolchain_io.WINDOWS` to True and `os.stat` to report `st_nlink` 1 and 2: the chmod is called once and not at all). Mutations: ignore `st_nlink`; compare with `>= 1`.
