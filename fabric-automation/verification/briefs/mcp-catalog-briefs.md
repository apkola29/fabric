# Verification of the catalog of MCP servers: the briefs of the seven rounds, for three families

The briefs that the reviewing families were given in the seven rounds that checked `toolchain/catalog.json` and the text that is generated from it. The first round divided the servers, the next four closed what the round before had changed (the slices rotated), the sixth closed the fifth, and the seventh was a small follow-up by two families on the fixes of the sixth. Round 1 explains the task, the verdicts and the row format; each later brief names the earlier ones as its background.

## Round 1

You are one of three model families (GPT 6.1 Sol, Gemini 4 Argon, Grok 4.7) that check the work of a fourth (a Claude-family model that wrote it). Be adversarial and honest. Nobody wants a green report: a statement that you could not confirm is worth more than a "looks fine".

### What this is

The project is a "Fabric Code Factory": agents (and people with agents) plan, implement and verify changes to Microsoft Fabric, Power BI and Azure items. The agents must know which MCP servers exist, which of their tools only read, which change things, and which tools they must NEVER call. That knowledge used to be typed by hand into the instruction file that every session reads (`AGENTS.md`) and could drift from Microsoft Learn. It is now written ONCE, in `toolchain/catalog.json`, which the writer filled from the pages of Microsoft Learn (and the READMEs they link, on GitHub). The tables of servers in `AGENTS.md` (between `<!-- BEGIN GENERATED name -->` and `<!-- END GENERATED name -->` comments) and the reference `toolchain/skills/factory-router/references/mcp-servers.md` are GENERATED from the catalog, the manifest (`toolchain.json`) and the lock (a record of what the pinned stdio servers reported when they were launched). So an error in the catalog is an error in every session.

The user asked for: "fix the knowledge and skills and mcp servers and tools section by visiting each of the articles on Learn", starting from two articles: the Fabric Core MCP Server tools reference and "Choose a Microsoft Fabric MCP server" (the directory).

Risk tiers that matter for the flags: the factory refuses, in this version, any change of security, row-level or object-level security (RLS, OLS, data access roles), permissions (roles), connections, sensitivity labels, schedules, capacity or tenant settings, a destructive write, and so on (tier T3). It never accepts a license for anyone, and never handles a token, key or password. A tool "flagged" in the catalog is never called by an agent: it changes one of those areas, accepts a license, or hands out a credential. A tool of kind `write` or `destructive` is not flagged: it needs a person's approval for each change, under another rule.

### Where (everything is under <review folder> ; treat it as READ-ONLY)

- `CLONE\new\` : the files to check, in their new state: `AGENTS.md`, `toolchain\catalog.json`, `toolchain\toolchain.json` (the manifest), `toolchain\skills\factory-router\SKILL.md`, `toolchain\skills\factory-router\references\mcp-servers.md` (generated), `toolchain\instructions\factory-preamble.md` (the rules of a job), `toolchain\README.md`, `scripts\toolchain_catalog.py` (the validator and generator), `scripts\toolchain_py_instructions_extract.py` (the command), `scripts\test_CatalogTests_extract.py` (its tests), `scripts\facts.json` (the weekly fact check; the new claims are the ones whose ids start with `page-updated-cat-`, `page-catalog-tools-` or `gh-`), and `verification\tools\catalog_quotes.py` (the program that checks your quotes).
- `CLONE\old\` : the same files before this change (where there was one), and `CLONE\diffs\` : the unified diffs, old to new.
- `catalog-sources\` : the pages that the catalog cites, reduced to text, one file per page. Pages of Microsoft Learn are `<slug>.md` (the address after `learn.microsoft.com/`, other characters turned into hyphens); each starts with `SOURCE:`, `UPDATED_AT:` (the date that the catalog records), `MS_DATE:` and `TITLE:`. Pages of GitHub are `gh-<slug>.md` (the raw README or file), starting with a `SOURCE:` line. A reduction can lose formatting (tables become `|` lines). If a point looks missing or garbled, read the live page at its address (public, read only) before you decide.
- `briefs\checklist-<your slice>.txt` : the statements that you have to verify, one row each, with the id that your report must use and the pages that the row's server cites.

### Task A (everyone): verify each statement of your checklist against the pages

For every id of your checklist give ONE row. The id forms: `<server>:use` (what the server is for), `<server>:where` (where it runs, how it is reached, the group, whether the directory lists it, how it signs in; for a pinned server the sign-in comes from the manifest: `Entra` means Microsoft Entra delegated sign-in as the person, `Azure identity` means `az login` or a service principal or workload identity, `none` means no sign-in), `<server>:stage` (the release stage as the pages state it; "not stated on the pages that were read" must be TRUE: look for the words preview, public preview, generally available, GA, beta anywhere on the cited pages), `<server>#N` (a sentence about what it needs or its limits), `<server>:tools` (the list of tools by kind, and, for a server whose list comes from the lock, only whether the pages contradict it), `<server>:flagged` (the tools that no agent calls, with their area), `<server>:knowledge` (the tools that give knowledge), `directory`, `skills#N`.

Verdicts (one letter):

- S SUPPORTED: every part of the statement (names, numbers, conditions, states such as preview, exact spelling of tool and setting names) is on a cited page, and the statement does not claim more than the page does.
- P PARTLY: some part is not on the pages or is stronger than they say. Say which, and quote the page.
- U UNSUPPORTED: the pages do not say it.
- M MISLEADING: each word can be found, but the meaning changes (a condition dropped, "may" turned into "must", a preview shown as general, an example turned into a rule).
- T WRONG KIND OR FLAG: for `:tools` and `:flagged`, a tool whose kind (read, write, destructive) does not fit what its page says it does; a tool that changes security, RLS or OLS, permissions, connections, schedules, capacity or tenant or workspace settings, labels, credentials or a license and is NOT flagged; or a tool that is flagged and does not belong to its area. Name the tool.
- C CONFLICT: this statement and another one (of the catalog, the generated text or the instruction files) cannot both be followed or both be true.
- X OTHER defect (a tool on the page that the list omits or a tool that the pages do not name, a wrong count, a page that is cited and does not hold the point).

The row format is exactly `id | verdict | quote | reason` (one line each, with the vertical bars). The quote is at most 12 words, copied VERBATIM from a page that the row's server cites (join fragments with `...`); it is the text that shows the statement is right or wrong. A program looks every quote up on those pages; a row whose quote is not there shows that the statement was not read against the page. A statement that you could not confirm gets verdict P or U and says UNVERIFIED in the reason. For a `:tools` row of a server whose list is long, the quote can be the page line of one tool, and your reason must list every tool that is missing, invented or of the wrong kind. For the tools that a page lists with a description, judge the kind from that description: `read` only reads, `write` creates or changes, `destructive` deletes, removes or replaces (a tool that replaces a whole set, or cannot be undone, is destructive).

### Task B (everyone, on the servers of your slice): the flags

Read the tools of each server of your slice (on its pages, or in `mcp-servers.md` for a locked server) and decide whether any tool can change security, RLS or OLS, permissions, connections (data source connections and gateways), schedules, capacity or tenant or workspace settings, sensitivity labels, credentials (returns or takes a token, key or password), or a license, and is not flagged. Also decide whether a flagged tool is flagged for a reason that the pages support. Report each in your findings with the evidence. A tool that only creates, changes or deletes an ordinary item (a notebook, a pipeline, a file) is not flagged: it needs approval under another rule.

### Task C (your own text slice): the instruction text

Read the diffs in `CLONE\diffs\` and the new files. Look for: a contradiction between two files or between a file and the catalog; a rule that an agent could read the wrong way; a sentence that says something the catalog or the pages do not support; a safety rule that was weakened compared with `CLONE\old\`; a rule number or file name that does not exist; a generated table that is not valid or is misleading; a statement of what a check proves that it does not prove. The pinned wording of the old rules is held by tests, so a changed rule is a change on purpose: judge whether it is right.

### Rules for findings

Every finding needs the file and the line or heading, a quote of at most 12 words (the text of a page, or of the file you are criticising), and a suggested replacement. Rank by impact on an agent that trusts the text: High (a false or reversed statement; an agent would do something forbidden or skip a refusal), Medium (a lost condition, a wrong scope, a missing flag that matters), Low (precision). No style nits. Return the whole report inline in your final message, at most 6500 words, in this order: the rows of Task A, then `FINDINGS` (Tasks B and C, numbered F1, F2, ...), then `CHECKED AND FINE` (the number of rows with verdict S and a one-line statement of what you did NOT check). Do not rely on writing files.
