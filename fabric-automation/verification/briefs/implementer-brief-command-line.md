### D1-1 (Medium). `fetch` does not use the one validation path

`cmd_fetch` checks only a part of what `resolve_profile` (and so `render` and `install`) checks. A profile that fails `verify` for a reason that `fetch` does not look at (a locked upstream skill with lint findings in `agent` mode: V8; a repo-owned skill with the same name as a locked skill: V2; a bad repo-owned skill folder name) is still fetched.

Decision: in `cmd_fetch`, run `resolve_profile(manifest, profiles, lock, name, base=project.dir, deps=deps)` for each selected profile (it raises `ToolchainError` with every failure that `verify` reports for the profile), and take the skills and the shared folders to fetch from the result (`resolved["skills"]` entries have `source`, `plugin`, `name`; `resolved["shared"]` entries have `source`, `folder`). Keep everything else: the default selection (every profile that has skills), "nothing to fetch", `refuse_store_links`, quarantine, the vendor call, the output line. The old per-profile code (`select_skills`, `select_shared`, `repo_skill_findings` inside `cmd_fetch`) goes away; do not leave two paths.
Tests: (a) an agent profile whose locked skill carries a lint finding: `fetch --profile` exits 1 and the vendor stand-in is not called (and `verify` and `render` agree); (b) a repo-owned skill with the name of a locked skill: refused; (c) a bad repo-owned folder name: refused with the profile named; (d) `fetch` without `--profile` on the committed manifest, profiles and lock (read from the project, with a stand-in `vendor_skills`) selects exactly what the union of `resolve_profile` over every profile that has skills selects, and does not raise; (e) the existing fetch tests keep passing (change the expected message only if you must, and say so).
In your report say which statement of `toolchain/README.md` or `docs/04-design.md` section 3.13 about fetch or V11 could now be wrong or right (the author edits the documents).

### D1-2 (Medium). `read_version` and `at_pin` accept a pre-release as the pinned release

`EXACT_VERSION_RE` accepts a PEP 440 pre-release without a hyphen (`1.8.0rc1`, `1.8.0a1`, `1.8.0.post1`, `1.8.0.dev3` as far as the regex allows). `read_version` requires `-` or `+` before a suffix, so it reads `1.8.0rc1` as `1.8.0` and `at_pin("fab 1.8.0rc1", "1.8.0")` is True: `doctor` and `verify --live` say PASS for a pre-release.
Decision: `read_version` captures the suffix with the same grammar as `EXACT_VERSION_RE` (one definition: build the reading regex from the same suffix pattern, or share a constant), and `at_pin` compares the full thing as it does now (numeric parts zero-padded: `1.8` equals `1.8.0`; the suffix must match exactly; a pinned `1.8.0rc1` matches an installed `1.8.0rc1`, not `1.8.0`). Tests: `1.8.0rc1` vs pin `1.8.0` is not at the pin; `1.8.0rc1` vs pin `1.8.0rc1` is; `1.8.0a1` vs `1.8.0rc1` is not; `1.8.0` vs `1.8.0` is; `1.8` vs `1.8.0` is (existing); `fab 1.8.0-beta.2` and `+build` forms keep their current behaviour (existing tests). One test through `doctor` or `verify --live` for the pre-release case.

### D1-3 (Medium to Low, hardening). Places that read, write or delete through a link

The kit's rule is that it never writes or deletes through a symbolic link or a Windows junction. Four places still do:
1. `cmd_lock` and `cmd_update` (through `build_lock` and `resolve_source`) create and delete folders under `.factory/pack/.cache/<commit>` without `refuse_store_links`; a link at `.factory`, `.factory/pack` or `.factory/pack/.cache` is followed. Decision: call `refuse_store_links(project, deps, project.store())` in both commands before `build_lock` whenever `build_lock` will be called (not for `lock --no-network`, which resolves nothing). Tests: a link (real, and mocked variant) makes both commands exit 1 with the existing message and create nothing behind it.
2. `copy_tree` tests `(Path(folder) / entry).is_symlink()`, which is False for a Windows junction, and never tests `source` itself. Decision: use the junction-aware link test that `refuse_links` uses (find it; do not invent a second one) for `source` and for every entry of every folder it walks, and refuse with the existing message. Tests: a symbolic link and a junction as an entry, and a link as `source`.
3. `repo_skill_folders` (the folders of `toolchain/skills`) and `instruction_problems` (the files of `toolchain/instructions`) follow a link at `toolchain/skills`, at `toolchain/skills/<name>`, or at a parent folder of an instructions file. Decision: refuse a link there with a `ToolchainError` (for `repo_skill_folders`) or a problem line (for `instruction_problems`), using the same junction-aware test. Real tests where the account can make a link, mocked-link tests everywhere.
4. `store_problems`: if it walks the pack, make it refuse a link inside the pack the same way (look at what `vendor_skills` and `refuse_links` already promise before you add anything; do not duplicate a check that exists).
Install writes to `.github/skills` etc. are already guarded; do not change them.

### D1-4 (Medium to Low). `verify --contracts` launches a server whose launch changed

`_check_contracts` refuses to launch when the contract's `package_version` differs from the lock, but not when the contract's `launch` digest differs from `launch_digest(server_launch(...))` of the manifest as it is now. The V10 FAIL of `profile_findings` is reported, and the changed launch line (from an unreviewed manifest edit) is still executed.
Decision: in `_check_contracts`, after the package-version check, when `contract.get("launch") != launch_digest(launch)`, add a WARN line `contract <key> was not launched: it was captured for another launch (...)` (the FAIL is already given by V10 of `profile_findings` for every profile that uses it; do not add a second FAIL) and `continue`. Also pass the added, removed and changed tool names of a drift message through `_clean_label`. Tests: with a changed launch in the manifest, `verify --contracts` never calls `probe_stdio` (assert the stand-in was not called) and still exits 1 because of V10; the drift message cleans a control character in a tool name.

### D1-5 (Medium). `lock --no-network` can write a lock that `lock` would not

(a) `refresh_digest` checks only the skill sources. If a package's `track` in the manifest changes to an exact version that the lock does not have (or a package is added), `current_launch` returns None, `refresh_digest` stamps the new `inputs_digest` and exits 0, and `verify` then fails V4. Decision: `refresh_digest` raises `ToolchainError("a changed package pin needs a lock with the network", [...])` when a declared package is not in the lock, or when its `track` is neither `latest` nor the locked version (write a `lock_package_problems(manifest, lock)` that returns `(missing, differs)` like `lock_source_problems`, and use it only here; do not change what `verify` reports).
(b) For a captured contract of a variant that no profile uses, whose launch changed, `refresh_digest` writes `skipped("launch changed")` while `build_lock` leaves the entry out, so `lock --no-network` followed by `lock --check` differs. Decision: `refresh_digest(manifest, old, deps, profiles=None)`; when `profiles` is given (`cmd_lock` passes `project.profiles`), a captured contract of a variant that is not in `used_variants(manifest, profiles)` and whose launch changed is dropped (with the same note), not replaced; a used variant keeps `skipped("launch changed")`. With `profiles=None` the old behaviour stays. Tests for (a): changed pin, added package, `latest` unchanged, same exact pin; for (b): used and unused variant, and `lock --no-network` then `lock --check` agree (exit 0) in a scenario with an unused captured variant whose launch changed.

### D1-6 (Medium). An unreadable or replaced managed folder crashes install, doctor and verify --live with a traceback

`toolchain_sources.SourceError` (raised by `deps.digest_tree` for a folder that is a file, has an unreadable file, or is too big) is caught only for an unmarked folder (`_has_content`). In `_managed_ops` (the managed branch and the removal loop), `skills_dir_problems` and `store_problems` it escapes, and `main` catches only `ToolchainError` and `OSError`: a managed skill folder replaced by a regular file makes `install --apply --force`, `doctor` and `verify --live` print a traceback.
Decision: (1) `main` also catches `toolchain_sources.SourceError` and prints the same kind of `error:` line as for a `ToolchainError` using `toolchain_io.safe_detail`, exit 1, no traceback (a safety net, tested); (2) `_managed_ops`: a managed folder that cannot be measured counts as modified (a conflict without `--force`, replaced with `--force`; in the removal loop: kept as a conflict without `--force`, removed with `--force`); (3) `skills_dir_problems` and `store_problems` report an unmeasurable folder as a problem line instead of raising; (4) `remove_tree` (and so `_copier` and `_remover`) must be able to delete a path that is a regular file or a link: if it is not a real directory, remove it with `os.unlink` (with `toolchain_io.make_writable` and `toolchain_io.retrying`), keep `shutil.rmtree` for a directory. Tests for each of the four, including the real scenario (a managed skill folder replaced by a file: plan shows a conflict, `--force` replaces it with the pinned folder and the run ends with 0 conflicts and no leftover folder, `doctor` and `verify --live` report a problem and do not crash).

### D1-8 (Low, partly accepted). The lock rules for a server name and version are weaker than the probe's

The probe (`toolchain_mcp._label`) refuses a name or version that `toolchain_mcp.suspect` calls token-like, host-like or an IPv4 address. The lock validation in `toolchain.py` (`SERVER_NAME_RE`, `SERVER_VERSION_RE`, `_check_contract`) uses weaker regexes, so a hand-written or foreign (candidate) lock with `server.version` = `1.host-1.com` or a 30-character token starting with a digit is accepted.
Decision: in the lock validation (`_check_contract` and wherever `SERVER_NAME_RE` and `SERVER_VERSION_RE` are applied to a lock), also reject a server name or version for which `toolchain_mcp.suspect(value)` is true (except the word `unknown`, which stays valid). `toolchain_mcp.suspect` exists (a public alias of `_suspect`); call it, do not copy it. DO NOT apply `suspect` to TOOL NAMES: the pinned Fabric server really has tools named `onelake_create-shortcut-adls-gen2`, `onelake_create-shortcut-amazon-s3` and `onelake_create-shortcut-s3-compatible`, and `suspect` flags all three (it reads them as token-like), so that rule would make the real `fabric-local/full` contract invalid. Tests: `1.host-1.com`, `1.web2.com`, an IPv4 address, a 30-character token starting with a digit and a name that is a host are invalid; `4.0.0-beta.4`, `1.6.0`, `1.30.0`, `unknown`, `Fabric MCP Server`, `fabric-rti-mcp-server`, `Azure MCP Server` are valid; the committed lock (all 5 captured contracts) still validates (this also guards tool names: add an assertion that those three real tool names are valid in a contract).

### D1-9 (Low). `probe_environment` hands a server an empty string where a host would use the default

`toolchain_mcp._declared_value` documents that a parent value counts when it is set and not empty (the way `${NAME:-default}` reads it in a host file). `probe_environment` resolves `base.get(item["from_env"], item.get("default"))`, so an operator variable set to `""` is passed as `""` instead of falling back to the default, or being left out when there is none.
Decision: treat an empty string as unset in `probe_environment` (default if there is one, otherwise leave the variable out). The license variable of the server itself is handed on only when the operator set it to a non-empty value too. Tests for: empty with default, empty without default, set, unset with default; and through `toolchain_mcp.capture_env` so that the two modules agree.
