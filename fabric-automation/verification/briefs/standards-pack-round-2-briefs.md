## Shared preamble (read first, then your slice)

You are verifying a drafted REFERENCE PACK for an open-source project: a "Fabric Code Factory" whose agents plan, test, implement and verify changes to Microsoft Fabric and Power BI items in a sandbox WITH NO NETWORK. The agents cannot read Microsoft Learn while they work, so the guidance they should apply is vendored in the repository as short checks: one line each, with an id, one sentence, where it applies, and the page and section that state it. The pack was drafted by one model (a Claude-family model) from 16 pages of learn.microsoft.com, verified once by three other families (GPT, Gemini, Grok), and corrected. This is the SECOND round. Round 1 found a defect in about every third line (a lost condition, a wrong scope, a wrong tag, an invented name, a copied run of words). Treat the corrected text as unverified: a fix can introduce a new defect, and a line that nobody questioned in round 1 can still be wrong.

The factory does NOT implement security, permission, network, sensitivity-label or tenant-setting changes in this version: it refuses and escalates them. So checks on those topics say to flag a change to a person and name the guidance (tag `[flag]`). The pack guides and never authorizes.

WHERE (everything is under <review folder>\pack2, treat it as READ-ONLY; make scratch copies under <review folder>\scratch-<your slice id> if you need to):

- The four pack files: `well-architected.md`, `security-and-governance.md`, `delivery-and-lifecycle.md`, `architecture-patterns.md`.
- `sources\`: the 16 pages, reduced to text, one file per page. Each starts with `SOURCE:` (the URL) and a date line (the page's `updated_at` metadata). Headings are lines that start with `#`. The reduction can lose formatting (tables become `|` lines, code becomes indented lines). If a point looks missing or garbled, read the live page at its URL (public, read only) before you decide. The file names and sizes are those of round 1.
- `DRAFTING-BRIEF.md`: the rules that the drafter was given (format, tags, truthfulness, exposure). Your yardstick. Two additions since: (a) a sentence may not copy more than 12 consecutive words of a page (a program checks this on the pack; judge meaning, not copying); (b) a check may name "Amazon S3" only as "the Amazon store that the page names", because the repository's validator reads the two-character name as a reference to a design identifier (this is intended, not a defect).

THE FORMAT. A line is: `- \`std-AREA-NN\` <one sentence, at most 35 words, ends with one tag [gate], [review] or [flag] where it helps> Applies to: <what a change touches>. Source: <label>, "<section heading of the page>"[; <label>, "<heading>"] [(control "<name>")].` The label is in the file's Sources table (label, page URL, the page's `updated_at` date, the day it was read). `Note:` lines record a tension between two places. Tags: `[gate]` a deterministic check could decide it from item definitions or the pull request (a name pattern, a missing setting, a file that must not be committed); `[review]` a reviewer's judgement; `[flag]` security, permission, network, sensitivity-label or tenant-setting topics, which the factory only flags; a sentence that starts `Ask:` needs knowledge that only the tenant has.

TRUTHFULNESS RULES the drafter had to follow: (1) paraphrase, never more than 12 consecutive words from a page; (2) never add a number, name, limit, feature, setting or recommendation that is not in the source text; numbers copied exactly; (3) never generalize beyond the text (a page that says "workspaces map to teams, projects or environments" must not become "always use one workspace per project"); (4) never merge two pages into one claim unless each supports its part and both are cited; (5) keep conditions ("when ... use ..."), tradeoffs and states such as preview or retiring; a permissive statement ("can", "may") must not become a requirement ("must", "does ... always"), and a disjunction ("A, B or C") must not become a conjunction.

HOW TO JUDGE A LINE. For each check, open the cited section (the heading must be a real heading of that page, and the point must be in that section or below it) and decide:

- SUPPORTED: every part of the sentence (numbers, names, conditions, tradeoffs, preview or retiring states, file and setting names with their exact spelling) is in the cited section, and the "Applies to" scope does not claim more than the page does.
- PARTLY: some part is not in the cited section or is stronger than the page. Say which part and quote the page.
- UNSUPPORTED: the page does not say it.
- MISLEADING: each word can be found, but the meaning changes in context (a condition dropped, a tradeoff inverted, a "may" turned into "must", an example turned into a rule, a preview feature presented as general, a recommendation turned into a restriction).
- WRONG TAG: a `[gate]` that no program could decide from item definitions and the pull request; a security, permission, network, label or tenant-setting topic that is not `[flag]`; a `[flag]` on something that is not one of those; an `Ask:` that does not need the tenant, or a tenant question without `Ask:`.
- WRONG CITATION: a heading that is not on the page, or that does not hold the point.
- CONFLICT: two checks, or a check and a `Note:`, that an agent cannot follow together without a rule that the pack does not give.

Also look for: a number that differs from the page by one digit; a name of a setting or feature spelled differently; a check that would make an agent DO something that the factory must not do (change a permission, a network setting, a label, a tenant or capacity setting, or delete or recreate something); text in the headers that claims more than the pages say.

RULES FOR FINDINGS. Be adversarial and honest. Every finding needs the evidence: the source file and heading, and a quote of at most 12 words, or the live URL and the sentence. A finding you could not confirm says UNVERIFIED. Rank by real impact on an agent that trusts the line (High: a false or reversed statement, or an agent would do something forbidden; Medium: a lost condition or a wrong scope; Low: wording, tag, or citation precision). No style nits. State a suggested replacement line for each finding (keep the format, at most 35 words in the sentence). Return the whole report inline in your final message, at most 3500 words. Do not rely on writing files. The report ends with "CHECKED AND FINE": the number of lines that you checked and found fully supported, and their ids.
