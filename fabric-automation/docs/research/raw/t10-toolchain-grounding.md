## 2. Versions and how they update

- `@microsoft/fabric-mcp` on npm: latest 1.6.0 (checked with `npm view` and with jsDelivr; the registry host itself was not reachable from the checking machine). NuGet `Microsoft.Fabric.Mcp` 1.6.0, published 2026-10-18. Release tag `Fabric.Mcp.Server-1.6.0` in https://github.com/microsoft/mcp .
- `@microsoft/powerbi-modeling-mcp`: 1.0.0 (checked: npm `latest`, and GitHub release `v1.0.0` of 2026-09-25 in https://github.com/microsoft/powerbi-modeling-mcp ). The documentation shows `@latest` in its example configuration.
- `microsoft-fabric-rti-mcp` on PyPI 0.6.2 (checked). `ms-fabric-cli` (the `fab` command) on PyPI 1.8.0 (checked); GitHub's latest release of https://github.com/microsoft/fabric-cli is v1.7.0, so the two disagree.
- The container image `mcr.microsoft.com/fabric/fabric-mcp`: the `latest` tag shows the metadata of 1.4.0, and a `1.6.0-amd64` tag exists with no plain `1.6.0` tag. Do not rely on `latest`.
- Pinning syntax: npm `package@version`; uvx `package@version`; dnx `Package@version`; Docker `image@sha256:<digest>`. None of the host configuration files has a version key of its own.
- Hosted servers update by Microsoft without notice. Only Fabric IQ documents a contract pin: send the header `X-Variants: Fabric.Routing.FabricIQ.V1` on every request (the `/v1` in the URL is not its contract version).
- Fabric REST specifications: https://github.com/microsoft/fabric-rest-api-specs (no GitHub releases).
- Bounding what a launch can resolve by date (**checked**, 2026-10-31). npm's `before` setting (the environment variable `npm_config_before`) limits resolution to versions that were available on or before a date, and `npm exec` honours it: with a date before the publication of `@microsoft/fabric-mcp` 1.6.0, npm 12.0.1 stopped with `ETARGET` and the message "No matching version found ... with a date before". uv has `UV_EXCLUDE_NEWER` (documented since uv 0.2.12; equivalent to `--exclude-newer`, which the uv command reference lists for `uv tool run`), which excludes distributions published after a date, compared with the upload time of each file. Both pages are facts in `scripts/facts.json`. Neither is a hash lock: a dependency that was published before the date and that nobody reviewed is still resolved.
- What the pinned packages pull in when they run (**checked**, 2026-10-31, with `npm view` and the PyPI metadata). The three npm servers (`@microsoft/fabric-mcp` 1.6.0, `@azure/mcp` 4.0.0-beta.4 and `@microsoft/powerbi-modeling-mcp` 1.0.0) declare no `dependencies`, only optional platform packages at exactly their own version, so their pin fixes everything that runs. The Python server `microsoft-fabric-rti-mcp` 0.6.2 declares ranges (`fastmcp<4,>=3.0`, `msal<2,>=1.32.0`, `azure-identity<2,>=1.24.0`, `httpx~=0.28.1` and two `azure-kusto` ranges). The two pinned command-line tools declare ranges too: `ms-fabric-cli` 1.8.0 (`msal<2,>=1.34`, `azure-identity>=1.25.0`, `fabric-cicd>=1.4.0` and others, with `pyyaml` and `psutil` exact) and `@microsoft/powerbi-report-authoring-cli` 0.5.0 (`ajv ^8.18.0`, `playwright ^1.48.0`, `commander ^13.0.0`, `powerbi-client ^2.25.0` and others). The NuGet package of the Bicep server was not examined. The two PyPI statements are facts in `scripts/facts.json`.

## 3. The Fabric local server's switches (**checked**, version 1.5.0, launched over stdio)

The server's README (https://github.com/microsoft/mcp/blob/main/servers/Fabric.Mcp.Server/README.md , **checked**) asks for Node.js 22 or later on the npm route and for the .NET 10 SDK on the dotnet-tool and `dnx` routes (a global tool built for .NET 10 reported "format version is higher than supported" under SDK 9 on the checking machine). `server start` takes `--mode single|namespace|all` (default namespace), `--namespace <name>` (repeatable), `--tool <name>` (repeatable; switches to all mode), `--read-only`, and a set of switches whose names start with `--dangerously-`. With `--mode all` the server lists 62 tools; with `--read-only` 34, all annotated as read-only; with `--namespace docs` 6 (API examples, best practices, item API spec, item definitions, item types, platform API spec), which need no sign-in. Without `--mode all` it lists 4 namespace tools (docs, onelake, core, datafactory). The same switches exist on the Azure MCP Server (same repository family).

## 4. Power BI Authoring (local): flags and license

From https://github.com/microsoft/powerbi-modeling-mcp (README, **checked**): `--start` (required), `--readonly` (safe mode, no writes), `--readwrite` (the default; a confirmation prompt before an edit is applied to the semantic model, once per database), `--compatibility`, `--authmode interactive|serviceprincipal`, `--accepteula`. The environment variable `PBI_MODELING_MCP_ACCEPT_EULA=true` does the same as `--accepteula`. "The MCP server blocks all other tool calls until you accept it." In an interactive session the agent can call an `accept_eula` tool after the user explicitly authorizes it. "Only use these options after you have reviewed and agreed to the EULA." Service-principal sign-in reads `AZURE_CLIENT_ID`, `AZURE_TENANT_ID` and `AZURE_CLIENT_SECRET` (or a certificate path and password). The variable `PBI_MODELING_MCP_ALLOWED_CONNECTION_HOSTS` lists extra hostnames (Analysis Services or XMLA endpoints) that the server may connect to; the README warns that access tokens are sent to those hosts, so the kit never passes it on and a capture or job must not inherit it.

On a machine whose npm points at a corporate package feed, `npx` of this package and of the Fabric server failed with `EALLOWREMOTE` ("Fetching packages of type remote have been disabled"). A hosted GitHub runner has no such feed.

## 8. The MCP protocol moved (**checked**)

Revision 2026-07-28 of the protocol (https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning.md ) is stateless: the `initialize` handshake, the `initialized` notification and the `Mcp-Session-Id` header are not part of it. Every request carries per-request metadata, HTTP requests carry `MCP-Protocol-Version`, `Mcp-Method` and `Mcp-Name` headers, and `server/discover` is the optional discovery call. The versions up to `2025-11-25` are "legacy". A dual-era client probes and falls back to `initialize`; a legacy client talking to a modern-only server fails, and the modern server should name its supported versions in the error. The servers read for this note answer both eras: the Fabric local server (1.5.0 and 1.6.0) and the Azure server (3.0.51) answer a `server/discover` call with a modern reply and an `initialize` call with the legacy handshake (a probe of 2026-10-31; before that, with the legacy handshake alone, they had looked legacy-only). A server that settles its era on its first request refuses the other era afterwards, so a probe that gives up on a silent `discover` has to start a new process before it tries `initialize`. The wait matters: the local Fabric server (1.5.0) took 4.6 seconds to answer `discover` on a loaded Windows machine (about 3 seconds on a quiet one), and a probe that waited 5 seconds recorded it as legacy in three runs out of four and as modern in the fourth, so the probe waits 20 seconds. A tool contract capture therefore has to speak both eras.
