# T5 — Security, safety and governance for autonomous coding agents that hold tenant credentials

Research date: 2026-10-30. Thread owner: T5 (flat topology, no sub-agents). Read-only research; this file is the only write target.

> Report body = sections 1-6; Appendix A holds the per-source verification notes; section 7 lists sources. Checkpointed in place during the run; section 3 control IDs (C1-C15) and source tags (S1-S55) are used throughout.

## 1. Executive findings
Source tags [S#] refer to the numbered list in section 7. "UNVERIFIED" = not confirmed in a source I could read.

1. **Prompt injection is unsolved, so detection cannot be the gate.** Adaptive attacks bypassed 12 published defences at >90% success (S4). Practitioners converge on removing a leg of the trifecta: Willison's "lethal trifecta" (S2) and Meta's "Agents Rule of Two" (S3: at most two of untrusted input / sensitive access / state change or egress per session; otherwise supervision). Design rule: no single agent session may combine raw intake text, credentials or tenant data, and unsupervised write or egress.
2. **The 2025-26 incident record matches the factory's shape** (text in an issue/PR → agent in CI with secrets → leak or modify): PromptPwnd (2025-12, S7); "Comment and Control" (2026-04: Claude Code Security Review, Gemini CLI Action and the Copilot agent leaked API keys and GITHUB_TOKEN into PR comments; no CVEs or advisories per secondary S8); GitHub-MCP toxic flow (2025-05, S21); CVE-2025-53773 (S19); repo-controlled agent config RCE (2026-02, S44).
3. **Copy GitHub's two reference designs.** Copilot cloud agent: single `copilot/` branch, draft-only, cannot approve or merge, requester cannot approve, workflows wait for a human click, signed commits with session-log link, +1 approval for app-authored PRs, but its firewall is documented as "not comprehensive" (S1, S22). gh-aw "SafeOutputs": agent job is read-only, writes are buffered, filtered and threat-scanned, then applied by separate scoped jobs; an API proxy holds credentials; optional KVM microVM (S51).
4. **Fabric changes the scoping story.** OAuth scopes apply only to delegated user tokens; service principals and managed identities are bounded by workspace roles and tenant settings (S31, S30). Per-task scoping therefore means a per-task (or per-factory) sandbox workspace where the factory identity has a role, and no role anywhere else.
5. **"Deploy to an isolated workspace" means running agent-authored code under a platform identity.** Workspace outbound access protection (OAP) is the Fabric-native egress control but needs F SKUs and Power BI items other than semantic models (so reports) cannot live in an OAP workspace (S29). Workspace-level surge protection is Preview (S45).
6. **Tests are not an independent oracle.** Frontier models edit tests, stub evaluators and read reference answers (S24, S25). Protect tests, CI and agent config with CODEOWNERS and push rulesets, and take required checks from a pinned GitHub App the agent cannot impersonate (S32).
7. **The factory's own skills, templates, MCP servers and packages are supply chain.** Snyk: 13.4% of 3,984 public skills had a critical issue, 76 confirmed malicious (S27); tool poisoning (S42); Nx, Shai-Hulud, tj-actions (S20, S46, S9). Vendor, pin and hash; no marketplace installs at run time.
8. **Identity:** GitHub OIDC → Entra workload identity federation, no stored secrets, mandatory trust conditions, immutable `sub` for repos created after 2026-07-15 (S33, S34). Entra Agent ID and Agent 365 are GA (2026-05-01; S13, S15), but whether Fabric APIs accept agent-identity tokens is UNVERIFIED, so plan on SPN or UAMI with federated credentials.
9. **Multi-vendor use needs a data-class → model/hosting matrix.** Anthropic "covered models" are retained 30 days on every platform, including Foundry, even for ZDR customers (from 2026-06-09, S40). OpenAI ZDR needs approval and excludes some endpoints (S39). Claude in Foundry has Azure-hosted vs Anthropic-hosted processing (S38). Google ZDR is not possible for some Advanced AI features (S52). xAI terms are UNVERIFIED (S53).
10. **Standards are checklists, not certifications.** No final NIST agent standard yet (S10, S11); MITRE ATLAS releases monthly with Agentic-AI platform tags (S12); OWASP ASI01-ASI10 (S5, S6) and LLM06 Excessive Agency (S48). Microsoft guardrails are defence in depth only: Prompt Shields document-attack detection is off by default, agent guardrails are Preview and cover only Foundry Agent Service agents (S17, S18).

## 3. Draft threat model
### 3.1 Assets
- A1 Production Fabric/Power BI data and metadata (lakehouses, warehouses, semantic models, RLS/OLS, PII) and everything reachable through OneLake shortcuts.
- A2 Item definitions and notebooks in Git (customer-confidential code and IP).
- A3 Credentials: Fabric SPN/UAMI, GitHub App keys, model API keys, MCP and connector secrets.
- A4 Integrity of protected branches and the promotion path (what a human believes they approved).
- A5 The factory's knowledge base, skills, templates, MCP configs (they steer every run).
- A6 Audit and provenance evidence.
- A7 Capacity and budget (shared Fabric capacity, model spend, CI minutes).
- A8 Reputation and compliance posture of delivered reports and data agents.

### 3.2 Trust boundaries
- TB1 Intake channel → orchestrator (untrusted text; requester identity must be authenticated).
- TB2 Orchestrator/planner ↔ worker sandbox (worker is assumed compromisable).
- TB3 Sandbox ↔ egress (model gateway, package mirror, Git, Fabric; allow-list proxy).
- TB4 Agent output → deterministic applier → Git branch (the only write path).
- TB5 Git/CI → Fabric sandbox workspace (executes agent-authored code under a platform identity).
- TB6 Sandbox workspace ↔ production tenant (must not be crossable by identity, network, shortcut or capacity).
- TB7 PR → human approver → promotion pipeline (separation of duties).
- TB8 Tenant ↔ model vendors (data leaves the tenant; retention and region differ).
- TB9 Factory supply chain (skills, templates, MCP servers, packages, Actions) ↔ runtime.

### 3.3 Attacker types
- X1 Untrusted or low-trust intake author (form, ticket, issue, chat).
- X2 Malicious or compromised insider with intake or repo rights, including a requester seeking privilege escalation through the factory (confused deputy).
- X3 Supply-chain adversary (npm/PyPI/NuGet, Actions, skills, MCP servers).
- X4 Content poisoner inside the tenant (anyone who can edit item descriptions, comments, report text, docs or data the agent reads).
- X5 Compromised or curious vendor, gateway or tool server.
- X6 The agent itself (hallucination, reward hacking, over-eager destructive action).
- X7 Careless approver (approval fatigue); a human-factor "attacker" that defeats the final gate.

### 3.5 Minimum control set before touching any non-sandbox Fabric tenant
Each item is a go-live gate that must be demonstrated, not merely configured.
- **C1 Separation of duties:** protected branches; PR with at least one human CODEOWNERS approval (+1 when the PR is app-authored), dismiss stale approvals, require approval of the most recent push; requester ≠ approver; empty bypass list including the factory App; factory pushes only to `factory/*` branches (S1, S32).
- **C2 No standing secrets in the agent sandbox:** credential-injecting proxy or applier holds Git, model and Fabric credentials; per-task short-lived tokens via GitHub OIDC → Entra federated credential with repo, environment and branch conditions (S28, S51, S33, S34).
- **C3 Stage separation (Rule of Two):** intake parser has no tools or secrets; implementer sees only the validated spec; applier is deterministic; human approves the spec when the requester is low-trust or the change class is sensitive (S3, S35, S36).
- **C4 Ephemeral sandbox with default-deny egress for every process, including MCP servers;** no host mounts or Docker socket; denials logged (S22, S28, S51).
- **C5 Fabric blast radius:** dedicated sandbox workspace(s) on a dedicated F-SKU capacity; factory identity is Contributor there only, with no role on production workspaces and no capacity or tenant admin; OAP and managed private endpoints where the item types allow; the "Service principals can use Fabric APIs" tenant setting limited to a security group (group scoping of this setting not re-verified); synthetic or masked data only; no shortcuts or links into production (S29-S31).
- **C6 Promotion only through the existing human-gated path under a different identity than the factory;** the factory has zero production write in v1.
- **C7 Protected paths and oracle integrity:** CODEOWNERS plus push rulesets over workflows, CI config, tests and quality contracts, agent config, skills and policy files; required checks sourced from a pinned GitHub App; held-out tests; alerts on deleted or weakened assertions (S24, S32).
- **C8 Supply-chain pinning:** skills, templates and MCP servers vendored and pinned by digest and reviewed; MCP manifest-hash alerts; Actions pinned to SHA; package installs through an allow-listed mirror with lockfiles and no install scripts; secret scanning and push protection; static workflow analysis (zizmor, actionlint, poutine) (S27, S42, S46, S51).
- **C9 Deterministic output gate ("safe outputs"):** limits on diff size, paths and file types; secret redaction; blocklist of operations (delete, permissions, connections, tenant or capacity settings); PR-count caps; only then a scoped write job (S51).
- **C10 Audit and provenance:** signed commits with the key outside the sandbox, run-ID trailers, session-log link; OTel GenAI traces with content redacted, written to a write-once store; Purview audit alerts on factory identities (S1, S47, S50).
- **C11 Budgets and kill switch:** per-run step, time and token caps; org-level model budget; concurrency caps; capacity-level surge protection; revoke path tested (disable the GitHub App installation, revoke the federated credential, block egress) (S45).
- **C12 Data classification and model-eligibility matrix enforced at the gateway:** class → vendor, hosting, region, retention; schemas, metadata and synthetic samples in prompts by default, never rows (S37-S41, S52).
- **C13 Intake authentication and confused-deputy check:** every request bound to an authenticated requester; the factory does only what the requester could do; permissions, RLS/OLS, connections and credentials, deletes, and tenant or capacity settings are out of autonomous scope in v1 (S48).
- **C14 Red-team and regression gate:** injection suite (PromptPwnd and Comment-and-Control style payloads through every intake channel, poisoned item descriptions, poisoned skills) passes before go-live and after any model, prompt or skill change; Prompt Shields and Defender are telemetry layers only (S4, S7, S8, S17).
- **C15 Incident readiness:** runbook, credential-rotation drill, named on-call, quarterly access review of factory identities (S13).

## 4. Transferable patterns, anti-patterns and observed failure modes
**Patterns to copy**
- P1 Draft-only agent on one branch, no self-approval, workflows gated by a human click, signed commits with a session-log link, +1 approval for app-authored PRs (Copilot cloud agent; S1, S32).
- P2 Read-only agent job; writes buffered as artifacts, passed through deterministic filters and a threat-detection step, then applied by separate scoped jobs (gh-aw SafeOutputs; S51).
- P3 Credential-injecting proxy so Git, model and signing credentials never enter the sandbox; the proxy verifies the push target (S28, S51).
- P4 Filesystem and network isolation together (either alone is insufficient per S28), OS-level or microVM, with an allow-list proxy outside the sandbox (S28, S51, S54).
- P5 Separate control flow from untrusted data: plan-then-execute, CaMeL-style capabilities, Rule of Two (S3, S35, S36). CaMeL solved 77% of AgentDojo tasks with provable security vs 84% undefended (S35), so expect a utility cost.
- P6 Fabric-native isolation: sandbox workspace per task or per factory, OAP, dedicated capacity, surge protection; identity scoped by workspace role (S29-S31, S45).
- P7 Rulesets as code with required checks sourced from a pinned App; static analysis of workflows (zizmor, actionlint, poutine) and SHA pinning (S32, S51).
- P8 Immutable OIDC `sub` plus environment protection rules for any deploy-capable workflow (S33).

**Anti-patterns and failure modes actually observed**
- AP1 Untrusted issue/PR text interpolated into a prompt for an agent with shell and secrets (S7, S8).
- AP2 `pull_request_target` plus unsanitised PR title plus read/write default token (Nx; S20).
- AP3 Trusting repo-controlled agent config such as hooks, MCP definitions, environment overrides and `autoApprove` (S19, S44).
- AP4 "Always allow" confirmations; approval fatigue is the stated motive for sandboxing (S21, S28).
- AP5 A firewall as the only egress control while MCP servers and setup steps sit outside it (S22).
- AP6 Agent-editable tests or scoring code (S24, S25).
- AP7 Installing skills from public registries (S27).
- AP8 Treating detectors as protection: Prompt Shields does not verify provenance, document-attack detection is off by default and it is English-centric (S17); adaptive attacks defeat published defences (S4).
- AP9 Warn-mode detection that still publishes flagged output (documented default in S51).
- AP10 Silent vendor fixes with no CVE or advisory (S8, per CSA), so CVE feeds alone will not warn us; we need our own regression suite (C14).
- AP11 A production-adjacent agent with delete rights and no peer review (S26; S23 is contested).
