# T4 — Fabric and Power BI platform mechanics for a Git-backed, automated change pipeline

Thread: T4 (FEASIBILITY). Research date: 2026-10-30. Author: research subagent T4. Read-only research; this file is the only write target.
Legend: GA = generally available; PREVIEW = public preview; UNVERIFIED = could not confirm in a source I read. Facts carry a source tag [S#] resolved in section 7. My inferences are marked "INFERENCE".

## 1. Executive findings (max 10 bullets)

1. **Verdict: feasible with caveats.** The loop branch -> isolated workspace -> Git sync -> deploy -> tests -> PR works with Fabric REST plus a service principal (SP) for the core types (Git-untagged/GA: notebook, pipeline, lakehouse, eventhouse/eventstream, environment, variable library; Git-PREVIEW-tagged: semantic model, report, warehouse). There is NO one-call "branch out" API: automation = create Git branch (provider API) + Create Workspace (+capacity) + Git connect + initializeConnection + updateFromGit + post-deploy jobs (optionally the PREVIEW Create Workspace Relation API) [S2, S6, S11]. Microsoft's own CI/CD guide says Update-from-Git does not load data, bind connections or activate variable-library value sets [S23].
2. **SP coverage is per item type and is the largest design risk.** Update From Git and Bulk Import with an SP work "only when all items involved support service principals" [S12, S25]. S9 shows SP = No for ML experiment/model, Activator (Reflex), Digital twin builder, Mirrored database, Mirrored Azure Databricks catalog; data agents accept SPs only for ALM (Git/deployment pipelines), not for querying or evaluation [S20]. Mixed workspaces need exclusion or a user-identity fallback.
3. **Maturity is uneven.** PREVIEW per Microsoft: Git for semantic model and report (tag in S1), PBIR auto-conversion tenant setting [S63], data-agent source control and evaluation [S20, S45], ontology, warehouse Git [S67], workspace monitoring [S59], outbound access protection [S58], hosted Power BI Authoring MCP [S37]. Bulk Import/Export APIs carry conflicting labels (preview in S23, "generally available" in S25). fabric-cicd v1.4.0, Fabric CLI v1.7.0 and Terraform provider v1.14.0 are open source; the Terraform README says it is NOT covered by Microsoft support [S52-S56].
4. **MCP coverage (requester directive).** No MCP server covers Git integration, deployment pipelines, Job Scheduler runs, variable-library activation or report rendering. Hosted Core MCP (workspaces, items + definitions, folders, roles, OneLake shortcuts/security) documents only browser OAuth for a signed-in user, no SP [S36]; local Fabric MCP adds assign-capacity and run-pipeline but no definition get/update [tool registry]; Fabric IQ MCP is read-only DAX [S38]; Power BI Authoring MCP local (GA) edits models and runs DAX [S37]; DW/SQL-endpoint MCP has one tool, executeSQL (preview) [S39]. Design REST/`fab`/fabric-cicd-first; use MCP only as author-side tooling.
5. **Test mechanics exist for most types.** Notebook/pipeline runs via Job Scheduler with SP and `exitValue` [S27, S28]; Livy accepts SP tokens [S46]; DAX via executeQueries (SP only if the tenant switch is on and the model has no RLS/SSO; 120 queries/min; 100k rows) [S40]; report render via exportToFile (capacity required; SP cannot export sensitivity-labelled reports to PDF/PPTX) [S41, S42] or the skills' headless `powerbi-report-author preview --screenshot` [8.15 skills notes]; data-agent evaluation is a preview notebook SDK that likely needs a user identity (INFERENCE) [S45, S20].
6. **Isolation is feasible but cost/throttle behaviour needs a dedicated capacity.** Throttling is per capacity (10-minute overage protection, then delay/reject) [S50]; pause/resume (F SKU, ARM) resets it but bills the carry-forward and makes all content on the capacity unavailable [S49]; trial (60 days, F4/F64) lacks data agents/Copilot [S51]; deleting a workspace is a soft delete (default 7 days) and soft-deleted items keep incurring storage until permanently deleted; Git sync can re-create soft-deleted items with new IDs [S61, S3].
7. **Governance switches silently block automation.** SP switch #2 (create workspaces/connections/deployment pipelines) is off by default for new customers; the GitHub Git switch is off by default; connect/disconnect need workspace Admin; workspace inbound protection blocks Git APIs outside the VNet, branch-out and deployment pipelines; OAP (preview) blocks Git unless allowed per workspace; none of these settings are copied to a new workspace; labelled items need an export switch [S30, S57, S58, S3].
8. **AI-authored files must match Fabric's serializer** (LF, no trailing newline; Commit deletes non-definition files inside item folders; 25 MB/file, 1,000 items/workspace, GitHub 50 MB and ADO-SP 25 MB per commit) or every sync shows phantom diffs [S3; git-integration-operations-cli].
9. **Promotion path:** Git sync alone leaves environment-specific settings to post-sync jobs; deployment pipelines have UI-only rules/pairing, no compare API, a 300-item cap and no support under inbound protection [S31, S32, S58; deployment-pipelines-authoring-cli]; fabric-cicd is the code-first option (full deploy, parameter.yml, SP) with documented per-type gaps (warehouse and SQL DB shells only) [S53, S54].
10. **Skills-for-Fabric (plugin v0.3.19) is consistent with Learn on the main mechanics** and adds operational gotchas (stale workspaceHead, one Git op at a time, API does not create the Git folder), but only the Git skill declares `maturity: experimental` and a few items drift from Learn (section 6).

## 3. Transferable patterns, anti-patterns and failure modes

**Patterns (evidence-backed)**
- **Git is the single source of truth; workspaces are disposable consumers.** One writer per branch; the factory commits to Git (PR), never both workspace-commit and automation-push on the same branch [git-integration-operations-cli; S23].
- **Ephemeral feature workspace on a dedicated factory capacity:** create branch -> Create Workspace(capacityId) -> assign factory SP Admin -> git/connect (ConfiguredConnection) -> initializeConnection(PreferRemote) -> updateFromGit(allowOverrideItems) -> poll until workspaceHead == remoteCommitHash -> post-deploy jobs -> tests -> teardown (delete + permanent delete) [S2, S23, S61, skill]. Microsoft documents both "create/delete per branch" and "recycle" lifecycles [S23].
- **Two planes:** definition plane (Git) vs item-state plane (active value set, connections, schedules owner, data). Automate the second plane explicitly [variable-library-cli; S23, S68].
- **Static checks first (no capacity):** TMDL/TMSL and PBIR JSON-schema validation (`powerbi-report-author validate`), SQL project build, KQL schema script review, notebook lint, `.platform`/logicalId integrity, LF/no-trailing-newline check [S34, skills].
- **Functional tests as Fabric-hosted notebooks** run through Job Scheduler (SP) that return `exitValue`; DAX assertions via executeQueries or Semantic Link with `set_service_principal`; visual regression via exportToFile or headless screenshots [S28, S29, S40, S41].
- **Normalised definition diff** (strip auto-rebound ids) to decide what changed; never hash raw getDefinition [deployment-pipelines-authoring-cli].
- **MCP only for author-side help** (Power BI Authoring MCP local for model edits/DAX) while control-plane steps stay in code [S37; semantic-model-authoring Tier 1].
- **Model/data quality:** Semantic Link Labs v0.18.0 (notebook-only; Best Practice Analyzer, Vertipaq Analyzer) can run inside the tested workspace [S23, S71]; table-level data quality (profiling, rules, scans on Delta tables) is a separate Microsoft Purview product, SPN-based, not a Fabric item API [S70]; no in-Fabric data-quality REST feature was found (UNVERIFIED).

**Anti-patterns / failure modes actually documented**
- Treating Update-from-Git as a full deployment (no data, no connections, no value-set activation) [S23].
- AI agents writing trailing newlines/CRLF -> phantom "uncommitted" diffs after every sync [git skill].
- Concurrent Git operations or stale workspaceHead -> corrupted head tracking / 400 [git skill].
- Sharing a capacity with production: one runaway test pushes the whole capacity into interactive rejection [S50].
- Assuming delete = cost stop: soft-deleted workspaces/items keep storage cost; Git sync can resurrect soft-deleted items with new IDs [S61, S3].
- Scheduled jobs travel in `.schedules`; ephemeral workspaces and "uncommitted" schedule diffs can surprise automation; schedulers auto-disable after ~10 consecutive failures [S68].
- Relying on SP for items with SP = No, or for data-agent runtime calls [S9, S20].

## 5. Top 15 automation blockers / sharp edges

1. **SP-support gaps break SP-driven Git sync/bulk import** for any workspace containing ML, Activator, Digital twin builder or mirrored DBs; data agents SP-only-for-ALM [S9, S12, S20].
2. **Workspace creation by SP needs the off-by-default switch #2** plus capacity-contributor rights; Git connect/disconnect needs workspace Admin [S26, S30, S3].
3. **"Branch out" is a UI feature**; automating it means five+ separate calls and a PREVIEW relation API; the delegated self-service model is only "planned" [S6, S11, S23].
4. **Post-deploy gap:** data, connections, value-set activation, semantic-model binding and refresh are not done by Git sync; connections are not source-controlled [S23, S54].
5. **Git operation serialization:** one op at a time, stale workspaceHead => 400, status itself may be 202, commit and update cannot run together [S3; git skill].
6. **Serializer fidelity:** LF/no trailing newline, Commit deletes foreign files in item folders, 25 MB/file, 250-char paths, 1,000 items, GitHub 50 MB / ADO-SP 25 MB per commit [S3; git skill].
7. **Git connection prerequisites:** API does not create the target directory; GitHub needs a PAT-backed connection and an off-by-default switch; SPs need ConfiguredConnection (PrincipalTypeNotSupported otherwise); switches apply to the acting Fabric user/SP group [S57; git skill].
8. **Capacity-wide throttling and trial limits:** shared capacity risk; trial lacks data agents/Copilot and has limited count; pause blocks everything [S49-S51].
9. **Soft delete and resurrection:** cost continues and Git may re-create items with new IDs [S61, S3].
10. **Schedules in Git (`.schedules`)** can activate jobs in test workspaces; schedule owner is the last modifier; auto-disable after repeated failures [S68].
11. **Data-agent automation is thin:** preview Git, SP only for ALM, evaluation SDK is a preview notebook flow, trial excluded, `published/` is generated [S20, S45, S51].
12. **DAX test limits:** executeQueries SP not allowed for RLS/SSO models, needs two tenant switches, 120/min, 100k rows, one table, no INFO functions [S40].
13. **Report render limits:** capacity-backed only (not PPU), SP cannot export labelled reports to PDF/PPTX, custom/R/Python/ArcGIS visuals fail, PBIR vs deployment pipelines conflict [S41, S42, S32].
14. **Network/sensitivity governance:** inbound protection blocks Git APIs outside the VNet, branch-out and deployment pipelines; OAP (preview) blocks Git until allowed per workspace; settings are not copied; labels block export without a switch; from 2027-02-28 users without read-write on items cannot use Git [S3, S57, S58].
15. **Warehouse/SQL DB are DDL problems:** Git for warehouse is preview, SQL-project based, cyclic dependencies and collation break branch-out; fabric-cicd deploys only the shell [S54, S67].
