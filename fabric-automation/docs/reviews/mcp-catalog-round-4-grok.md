## FINDINGS

F1. Medium. `toolchain/catalog.json`, `fabric-rti-local` connections changes (the sentence at the external-table example). Quote: `eventstream_add_eventhouse_destination`, `eventstream_add_custom_endpoint_destination`. The README names those tools, plus `eventstream_add_custom_endpoint_source`, as sources and destinations, and says `eventstream_update` modifies destinations. The lock annotates the add-tools as neither read-only nor destructive. The connections statement names only `kusto_command`. A session can add a source or destination after approval, and rule 10 will not refuse it. This is the same class as the Data Factory definition binding that round 4 just refused. Suggested replacement: add "a call of `eventstream_add_custom_endpoint_source`, `eventstream_add_custom_endpoint_destination`, `eventstream_add_eventhouse_destination` or `eventstream_update` that adds or changes a source or a destination".

F2. Low. `toolchain/catalog.json` line 537, `azure-mcp` area capacity, tenant or workspace settings. Quote: for example a Fabric capacity. The cited pages support a quota or limit (`quota`), a disk SKU change, and "Update VMSS 'my-vmss' capacity to 5 instances". They do not support a Fabric capacity, a management group, or a setting of a tenant or a subscription. Suggested replacement: "a change of a quota or a limit (`quota`), of the SKU of a resource, or of the capacity of a resource, for example a virtual machine scale set, through any namespace".

F3. Low. `toolchain/catalog.json` line 864, `datafactory-local` needs. Quote: Copilot calls `mcp_datafactorymc_create_pipeline_schedule` with a recurrence. The needs sentence is true about the limitation line and about the README, but a reader can take it as the pipelines page denying schedule tools. That page also documents creating a schedule. The tools stay never-called, so this does not authorize a call. Suggested replacement: "The pipelines page says deletion and schedule modification are not available through the MCP server, and the same page documents creating a schedule; the README also lists `set_pipeline_schedule_enabled`: the pages disagree about modification."

F4. Medium. `AGENTS.md` line 12, rule 6, against `mcp-servers.md` line 12. Quote: Before anything that changes a tenant. The preamble, How to work rule 2, uses the same six words. The reference header says a call that changes the live state of a tenant or of Azure needs the approval those rules ask for. Round 4's `azure-arm-cost` use and `fabric-sql` needs now say a live Azure or live-state change needs that approval, and they no longer say the change is a change of a tenant. An agent that follows rule 6's own words can skip the approval the new sentences say the rules ask for. Suggested replacement: in both rules, "Before anything that changes the live state of a tenant or of Azure".
