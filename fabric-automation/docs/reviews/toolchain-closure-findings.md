# Closure review of the toolchain kit: findings, checks and outcomes

The corrected toolchain kit (commit `a7932d1bf9`, the one that followed the first review in [toolchain-review-findings.md](toolchain-review-findings.md)) was reviewed a second time by three model families. Each worked in its own clean clone of the public repository, on a slice that a different family had reviewed the first time. They were asked to try to break the fixes of the 36 earlier findings, to attack what was new, and to mutate the safeguards of their slice. This file says what they decided about the earlier findings, what new they found, how each new finding was checked, what was changed and how the change was proved. The replies are kept as the reviewers wrote them, with only the notation normalised.

## How each new finding was handled

The author re-read the cited code and either reproduced the finding on the published commit or checked it against the primary source, before accepting or rejecting anything. The reproductions are in a replay script (see below): 15 of the 20 are replayed there. The other five are not: R-N2-8 was read in the code, R-N3-1 was reproduced in the real project, R-N3-2 and R-N3-4 are statements about public package metadata and about a sibling folder, and R-N3-5 is a gap in the tests, which the mutations show. Nothing was rejected. Of the 20 new findings, 18 were accepted as rated and 2 with a lower rating (R-N1-6 and R-N2-5: the defect is real, the impact is smaller than stated). By the author's ratings that is 4 High, 8 Medium and 8 Low; the reviewers had rated 4 High, 10 Medium and 6 Low. One finding (R-N3-4) concerns a folder of the same repository that is not part of this project and is left untouched.

The fixes were made in two stages, as before. The author wrote what is not command-line code: the validator fix, the publish-script tests, the facts, the profiles, the lock fields, the documents and the workflow step. The command line and the helper modules were changed by the two implementation agents, each working from a written specification in its own copy (X: the command line and its tests, nine items; Y: the three helper modules and theirs, nine items). Each agent proved its safeguards by mutating a copy and checking that the test meant for the safeguard failed. The author read the production diff of both, merged it, and ran the whole suite, the replay and a real install.

## What the author added to the review

1. **The capture passed the operator's whole environment to a server.** The first review (R-B-3) found that a credential-free capture received registry tokens and proxy passwords, and the helper module was fixed: it passes a server only an allow-list and the variables the variant declares. The command line, however, handed the helper the operator's entire environment as the "declared" set, so the allow-list did nothing. No reviewer and neither agent saw it, because each side was tested with a stand-in for the other. It showed when the author composed the two real modules to check the date bound of R-N3-2: a stand-in server reported the three secrets that were set in the shell. It is present in both published commits. `probe_environment` now returns only the declared variables (each from the operator's environment or its default) and the license variable of the server that declares it, when the operator set it. Eight new tests (the function, its composition with the capture environment, the two commands, and a real server process that sees the date bound and none of three secrets) and eight mutations, all killed. The change is exercised on a hosted runner by the next capture, because a server now starts with less than before.
2. **The install failed on a folder that OneDrive was syncing.** In the first-run check in a scratch repository under the author's own OneDrive folder, `install --apply` stopped in 3 of 4 runs with `WinError 5, Access is denied` on the rename of a skill folder that had just been written (the sync client or the scanner has such a folder open for a moment). Each stop left some skills without their marker, and the next run reported them as 39 conflicts, so a person was stuck. Two changes. A move or delete that Windows refuses for that reason is tried again after growing pauses (about six seconds in all; on any other system a refusal is a real one and is not retried). And a folder that exists without a marker but holds exactly the pinned content is taken as it is, so that a half-finished install is finished by the next run; a folder with any other content, or one that cannot be measured, stays a conflict. After that 4 of 4 runs passed, and one of them was refused once and went through. 23 new tests (9 for the pauses, 5 for the swap of the store, 9 for the install) and 17 mutations.
3. **The recorded era of a server depended on how fast it started.** Probing the real local Fabric server (1.5.0) with the restricted environment gave `legacy` in three runs of four and `modern` in the fourth: the probe waited 5 seconds for `server/discover` and then started the server again for the older handshake, and on a loaded machine the server needed 4.6 seconds to answer. A contract that changes its era between runs is noise in every candidate lock. The wait is now 20 seconds (a server that never answers costs that once), a test holds it to between 15 and 30 seconds, and the real server answered `modern` in three runs of three afterwards.
4. **A delete that changed the mode of a file with two names, found by the first hosted run.** Removing a file or a folder first called `chmod` to make it writable. On Windows that clears the read-only attribute that git gives its objects, which a delete needs. On Linux the same call sets the mode of the file to write-only, and a file with two names (a hard link) shares that mode between them, so the other name became unreadable. The test of a configuration that is a hard link passed on Windows, where the call changes a flag and nothing else, and failed on the hosted Linux runner (run 41247839439: 1 error in 1,382 tests); the commit had been published by then, so the record says so. The clear now happens on Windows only, in one function of the io helper that the three places that delete use, and anywhere else the mode of a file is left alone, because a delete there depends on the folder. 5 new tests (3 for the function, one for the two deleting paths of the Git and skill helper and one for the folder removal of the command line, each with the exact path and mode checked) and 8 mutations (always, never, the wrong mode, each of the three call sites dropped, and two that pass the wrong path), all killed.
5. **The facts.** Four claims were added, so the list has 90 claims, from 86: npm's `before` setting and uv's `UV_EXCLUDE_NEWER` (and `npm exec` was run with a date before the package was published: it refused with `ETARGET`), and the dependency ranges of the Real-Time Intelligence server and of the Fabric CLI, from the PyPI metadata. The dependencies of the three npm servers and of the report authoring CLI were read with `npm view` (the note in the research folder records them).
6. **The lock.** The five captured contracts carry the launch digest and the capture date. The date is the day of the hosted capture, and the manifest's servers and modes were checked to be identical to the commit that the capture ran against. A later hosted capture is the cross-check.

## What was not changed, and what is still open

- R-C-5 stays unverified. The fact-check workflow now prints what `dotnet tool exec` offers on its .NET 10 runner, so the next run settles it.
- Dependencies are not locked by hash. The three npm servers need nothing but their own pinned platform packages; the Real-Time Intelligence server and the two command-line tools declare ranges. The date bound narrows this and does not close it.
- A candidate lock from a manual capture comes from a run that executes unreviewed packages. It is untrusted input for the review of a pull request.
- Hooks and alternates inside an existing cache folder of the pack are not neutralised; the digest check of the skills is the guard.
- Nothing has been run against a tenant, hosted servers are never captured, the Power BI license is never accepted by the kit, the unattended identity of each server is not proven (spikes S2 and S6), VS Code was not run, and the SQL endpoint tool name still needs a signed-in session.
- Reviewer C also noted that environment scrubbing does not sandbox a hostile package: it can change files of the same job. Neither workflow promotes an artifact automatically.
