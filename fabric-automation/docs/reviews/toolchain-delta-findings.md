# Delta review of the toolchain kit: findings, checks and outcomes

The toolchain kit as it stood after the second review (commit `abe6b9d614`: the corrections of [toolchain-closure-findings.md](toolchain-closure-findings.md), and the one fix that the first hosted run made necessary) was reviewed a third time by three model families. Each worked in its own clean clone of the public repository, on a slice that a different family had reviewed the second time, so that every family has now had every slice once. They were asked to read the delta from the commit of the second review (`a7932d1bf9`), to try to break the fixes of its 20 items, to attack what was new, and to mutate the safeguards of their slice. This file says what they decided about those items, what new they found, how each new finding was checked, what was changed and how the change was proved. The replies are kept as the reviewers wrote them, with only the notation normalised.

## How each new finding was handled

The author re-read the cited code and reproduced the finding, or checked it against the primary source, before accepting or rejecting anything. Thirteen are replayed in the replay script (see below): R-D1-1, R-D1-2, R-D1-3, R-D1-4, R-D1-5, R-D1-6, R-D1-7, R-D1-9, R-D2-1, R-D2-3, R-D2-4, R-D2-5 and R-D2-6. The others are not: R-D1-8 was checked against the committed lock (and the suggested fix was refused for tool names, below), R-D1-10 and the six surviving mutations are gaps in tests that the mutations themselves show, R-D2-2 needs a TLS server and has a real-process test, R-D2-7 and R-D2-8 are flaky tests, and R-D3-1 and R-D3-2 are statements about the SDK and the documents. Nothing was rejected outright. By the author's ratings that is 0 High, 6 Medium and 14 Low; the reviewers had rated 2 High, 10 Medium and 8 Low. The two High findings (R-D2-1 and R-D2-2) need either a folder planted in the Git-ignored pack folder, or a `.netrc` of the operator's own whose entry matches the host that the reviewed manifest names, so the author rated them Medium; the fix is the same size either way.

The fixes were made as before. The author wrote what is not command-line or helper code: the manifest and lock changes, the workflow, the replay scenarios, the facts and the documents. The command line and its tests were changed by one implementation agent (X: eleven items and two follow-ups) and the three helper modules and theirs by another (Y: six items and one follow-up), each in its own copy of the project from a written specification, each proving its safeguards by mutation (X killed all 174 mutations it wrote, Y all 47; the two it explained are an equivalent mutant and an invented one). The author read the production diff of both (+211 and −111 lines of command line, +80 and −33 lines of helpers; the tests grew by 1,527 and 874 lines), merged it, and ran the suite, the replay and a real first run. The author then applied 21 mutations of his own to the new safeguards of the merged code (the link refusals of `lock` and `update`, the launch check of `verify --contracts`, the package check of `lock --no-network`, the `SourceError` handler of `main`, the new cache, the empty operator value, the dotted suffix, the two uses of the probe's predicate, `fetch` and `copy_tree`, the removal of the old cache, the home folder, `http.emptyAuth`, the order of the 404 test, the revision check of `initialize`, the hard-link rule, and the `NETRC` and client-certificate variables): all were killed by the test meant for them. The tests of the four modules went from 535, 112, 137 and 277 to 628, 118, 146 and 307.

## Replay of the reviewers' reproductions

The replay script (38 scenarios from the two earlier reviews) was extended with 13 more, one for each finding that can be reproduced in a scratch copy with a scratch home folder, using stand-in servers, real Git and real junctions where the finding needs them. All 13 reproduce on the published commit `abe6b9d614` (13 of 13). Run against the corrected tree, all 51 scenarios give "not reproduced" (51 of 51; none was skipped on this Windows machine, and each one reports why it did not reproduce, for example that the vendor stand-in was not called or that the folder behind the junction is unchanged).

## What the author added to the review

1. **The .NET SDK was run.** Every reviewer and the first review could only repeat what Learn says. The author took the SDK 10.0.403 (the runner's version; the Windows x64 zip from the official download host, with a valid Microsoft signature) and a small tool package that prints its arguments, packed into a local feed, so that no network was needed. `dotnet tool exec --help` and `dotnet dnx --help` list no `--yes` or `-y`. Yet `dotnet tool exec PKG@1.0.0 --yes`, `dnx PKG@1.0.0 --yes`, `dnx -y PKG@1.0.0` and `dnx --yes PKG@1.0.0` all ran the tool with no argument, whereas an invented `--bogus-option` after the package reached the tool: the SDK takes `--yes` as a hidden option and does not pass it on. That refutes the claim of the first review (R-C-5) that `--yes` is rejected on .NET 10. Without `--yes` and with the input redirected, a first launch from a local feed ran at once. The root of the Linux tarball holds a `dnx` script next to `dotnet`, and the runner image readme lists the SDK but no `dnx`.
2. **The first use of the SDK by a user.** With a fresh home folder and none of the `DOTNET_` variables set (the probe passes a server only the variables that it declares), the SDK writes a banner and a telemetry notice to the error stream (not the output stream, so the protocol is not disturbed), says that usage data is collected, and generates a development certificate. `DOTNET_NOLOGO`, `DOTNET_CLI_TELEMETRY_OPTOUT`, `DOTNET_SKIP_FIRST_TIME_EXPERIENCE` and `DOTNET_GENERATE_ASPNET_CERTIFICATE` together removed the banner and skipped the certificate (the first two alone left the certificate step). The manifest now declares the four for the Bicep server, each with its default and an operator's own value winning, so a job or a session that launches it does not send telemetry or touch the certificate store of the user.
3. **The hosted capture of the corrected commit.** The facts workflow, dispatched with `capture` (run 41253985240), succeeded in every step: the update check found no upstream change, `verify --contracts` matched the five captured servers under the restricted environment and the date bound (0 failures, 10 warnings, all of them skipped or unavailable contracts), and the candidate lock that the capture kept is equal to the committed lock in every field (0 differences). That is the first cross-check of the stamped `launch` and `captured` fields on another run and another operating system. The validate workflow on the same commit (run 41253662975) ran 1,387 tests on Linux (77 skipped) and passed: it is the first Linux run of the fix of the `chmod` defect.
4. **The facts.** The claim about the runner image no longer says that its SDK "provides dnx".
5. **A Linux probe before the publication.** The hosted runner is the only Linux that the author has, and two earlier publications had failed there, so the author pushed the project files to a throw-away branch and dispatched the validate workflow on it before touching master. The first probe failed 31 tests, all of them tests of the validator: seven strings of four numbers in a row in the new tests of the command line, which the repository scanner reads as addresses (the publish gate would have stopped on the same check). No test of the toolchain failed on Linux (1,525 tests, 86 skipped), among them the real-symlink and real TLS tests that cannot run on the author's machine. The strings are built at run time now, and the second probe passed in 151 seconds. The time limit of the validate job was raised from 10 to 20 minutes, because the suite has grown.

## What was not changed, and what is still open

- R-N2-7: a long purely alphabetic label is accepted as a server name (above).
- The Bicep server has not yet been launched against the real package: the registry of NuGet is not reachable from the author's machine, and the next hosted capture is the test. Until a contract is recorded it is unverified, which matters in `dev` mode only.
- Whether Git for Windows offers the logon session of the operator to a server that answers with a Negotiate challenge was measured and not reproduced (no token was made for a loopback address), so `http.emptyAuth=false` is a precaution that is UNVERIFIED on a domain-joined machine.
- Things that the two implementers listed as seen and not changed: `lock --no-network` still keeps the non-captured contracts of an unused variant and the contracts of a removed server or variant (`lock` leaves them out); an unreadable skill in an offline `verify` now ends in an `error:` line instead of a V8 failure with the other findings; `lock` and `update --write`, `render --output` and `update --summary-file` write to a path that the operator names, without the link test; the reading functions of the Git module (`read_plugin`, `digest_git_tree`, `read_shared_entries`, `_has_commit`) trust the folder that they are given, which is safe because every caller passes a cache that was made in the same run, and `fetch_git` does not look at the folders above the cache folder, the callers do; `GIT_SSL_NO_VERIFY` and the proxy variables of the operator are honoured by the anonymous Git calls; the probe's child receives HOME, USERPROFILE and APPDATA, and the npm command line reads the operator's `.npmrc`.
- Nothing has been run against a tenant, hosted servers are never captured, the Power BI license is never accepted by the kit, the unattended identity of each server is not proven (spikes S2 and S6), VS Code was not run, and the SQL endpoint tool name still needs a signed-in session. The dependencies of the Real-Time Intelligence server and of the two command-line tools are not locked by hash.
- A candidate lock from a manual capture is the output of a run that executes package versions nobody has reviewed. It is untrusted input for the review of a pull request.
- The folder `fabric-monitoring-guides/capacity-metrics-app` of the same repository, which is not part of this project, holds two GUIDs in a pasted link. It is left untouched and reported to its owner.
