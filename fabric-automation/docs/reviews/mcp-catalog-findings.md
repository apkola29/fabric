# Verification of the catalog of MCP servers: findings, checks and outcomes

The catalog is `toolchain/catalog.json`, the one place where the kit says which MCP servers exist, where each runs, how it is reached, what it needs, which of its tools only read, change or delete, which tools no agent calls and which changes no agent makes, and which tools give knowledge. It was filled by a Claude-family model from the pages of Microsoft Learn that describe each server, and from the GitHub READMEs that those pages link (38 Learn pages and 12 GitHub files, each with the date that Microsoft gives for it). The tables of servers in `AGENTS.md` and the server reference of the router skill are **generated** from it, together with the manifest of the kit and the lock (what the pinned servers reported when they were launched): `python scripts/toolchain.py instructions --write` writes them, and `verify` fails (check V14) when a generated file is stale. Before this work the tables were typed by hand into the file that every session reads, and could drift from Learn.

The requester asked for it in these words: "fix the knowledge and skills and mcp servers and tools section by visiting each of the articles on Learn", starting from two articles, the tools reference of the Fabric Core MCP server and "Choose a Microsoft Fabric MCP server". The catalog has 24 servers (11 that the kit pins, 7 that the Fabric directory lists and the kit does not pin, 4 that Microsoft publishes outside the directory, 2 related ones that Microsoft does not host; 15 hosted, 8 local, 1 hosted by the customer). It lists 543 tools: the 70 namespaces and commands of the Azure server, whose kinds are the server's own annotations in the lock, and 473 more (214 read, 114 write, 53 destructive, 22 mixed). It names 33 tools that are never called and 34 changes that are never made through any tool (a statement of a change, such as a management command that changes who may access a cluster, or a definition that carries a connection), under nine areas: permissions, row-level or object-level security, security settings, capacity or tenant or workspace settings, connections, schedules, sensitivity labels, credentials and a license.

A model of one family (Claude) wrote it, and models of three other families (GPT 6.1 Sol, Gemini 4 Argon and Grok 4.7) checked it in seven rounds. In every round each family gave one row for each statement that it was asked to check, in the form `id | verdict | quote | reason`, where the quote is at most 12 words copied from a page that the statement's server cites and a program looked every quote up on those pages, so that a statement that was not read against its page shows. This record says what each round was, what it found, what was changed, where the reviewers disagreed and how that was settled, and what is still not proved. The reviewers' replies are kept as they wrote them, with the agent's own header removed.

The largest findings were these. (1) The Foundry server (79 tools) had no tool list and no flag, although it creates and deletes connections, schedules continuous evaluations and returns a SAS URL. (2) `executeSQL` of `fabric-sql` was flagged as never called while the router sends all T-SQL through it; the author split the flags into two kinds, tools that are never called and changes that are never made through any tool (a statement of the change, such as a statement that changes permissions), and rewrote rule 10 of `AGENTS.md`, the preamble and the router to say so. (3) The rule on contract drift treated the entry of a hosted server as a contract, which only a server that the lock measured has; the rule now says that for any other server the entry is a person's reading of its pages, so that a difference of names is reported before work goes on and, where the entry lists no tool, the agent says what the server listed. (4) The Azure server's `keyvault` namespace can return a secret, and `role` and `policy` change permissions and security; the Azure Resource Manager server's `create_deployment` and `create_or_update_resource` can change security resources, and `get_pricesheet_status` returns a SAS URL. (5) The generator said "none of its commands writes" for any variant of a server, a directory page without a date stopped it, and a tool that changes a protected area without a flag passed the validator; each got a test. (6) `datafactory-local` listed `get_access_token` as a write and left the sign-in and connection tools unflagged.

## Round 2

Each family took a slice that it had not taken and closed the round-1 findings of one other family (GPT those of Gemini, Gemini those of Grok, Grok those of GPT). The replies: [GPT](mcp-catalog-round-2-gpt.md), [Gemini](mcp-catalog-round-2-gemini.md), [Grok](mcp-catalog-round-2-grok.md).

20 findings: GPT 7 (1 High: Azure credential protection covered Key Vault outputs only), Gemini 8 (1 High: `security_role_operations` was flagged by name and the test of the job variants was vacuous where the lock holds no contract), Grok 5. The fixes: one statement of a change of credentials for any Azure namespace that returns or takes a secret, a key, a password, a connection string or a certificate (the read-only switch does not stop a read); statements for permissions, security settings, connections and schedules of the Azure server through any namespace; the same for the Azure Resource Manager server's two generic tools; a permission mode in the Foundry tool that creates a directory; six statements for `kusto_command` of the RTI server (permissions, row-level security, security settings, capacity, connections, credentials); statements for stored procedures of the SQL MCP Server; and the header of the reference, which said that a call that changes anything is a change of a tenant, now says that a call that changes the live state of a tenant or of Azure needs the approval that the rules ask for in a session and that a job makes no change through an MCP tool. The check of protected names moved from the tests into the validator, so that `verify` and `instructions` run it; it splits acronyms (`RLSRole` is `rls` and `role`) and keeps a short list of reviewed exceptions with their reasons (one: `activator_create_trigger`).

## Round 7

Round 6 had left one Medium and five Low findings, and all were fixed. Round 7 was a follow-up by two families on those fixes only: GPT ([reply](mcp-catalog-round-7-gpt.md)) closed the four findings that Grok had raised about claims of the fact list and re-read the other claims that had changed in rounds 5 and 6, trying 30 mutations of live page text of its own; Grok ([reply](mcp-catalog-round-7-grok.md)) closed the two findings that GPT had raised about the code.

Grok found the first finding fixed and the second partly fixed: the extractor of tool names accepted digits and hyphens, but no test held it (a revert still printed OK on the real README) and a name in a code span was still invisible. Both of its new points were Low and were fixed: a direct test of the extractor on a fixture of table rows (a digit, a hyphen, a dot, a code span, and a row that is not the first cell), an extractor that accepts a code span, and mutation c62 (the older pattern), which the test kills. The harness copies the folder `verification` now, so that a mutation of a verification tool can be tried.

GPT found all four findings partly fixed and raised 9 more (2 Medium, 7 Low). Its mutations of the live pages showed that a pattern still matched the beginning of a sentence: a condition added to the end of the billing or the restore sentence of the soft-delete page passed, the Data Factory requirement limited to one platform passed, an unsupported marker in front of a README bullet passed, and a negated Copy Activity in the Blob example passed. Five findings were fixed (the patterns of the soft-delete claim and of the Data Factory pipelines claim are whole sentences up to the full stop; the Blob example starts at the opening of its prompt; the bullets of the Eventstream and Map claims start at the beginning of a line), each with tests that the old pattern accepted. Of the 30 mutations 21 were not controls; 7 are detected now. The other 14 are not, and the author left them, with the reasons: they move or disavow the sentence in another place of the page (a section of removed features, a column of a table, a prompt marked as obsolete), which a pattern on the flattened text of a page cannot tell from the page's own sentence; a check of the structure of each page would, and was not written. The claims are drift detectors for the sentences that the catalog cites, and they are not proofs against a page that disavows its own sentence. Nobody read the last fixes.

## How the reviewers disagreed and how that was settled

- `executeSQL` and the two kinds of flag (round 1). Two families said that flagging the tool that the router sends all T-SQL through made the rules contradict each other. The author agreed, and a flag now is either a tool that is never called or a change that is never made through any tool, so that `executeSQL` is a `mixed` tool and the statement that is flagged is a statement that changes permissions or row-level security.
- The Foundry kinds (round 3). The page marks 44 tools as write; the catalog lists 14 of them as destructive (they delete, replace or regenerate). That is the writer's reading of the page, and the kinds of every server whose tools come from a page are the writer's reading, while the kinds of a locked server are the server's own annotations. The reviewers accepted the reading and the capacity statement.
- The Map tools (round 5). GPT asked for a connection statement for `map_create` and `map_update_definition`. The author first declined: the README's example adds a Lakehouse, an item of the workspace, and no page calls that a connection. The pinned build's source then showed that both tools take a free-form definition (`definition: dict`, written as `map.json`), which is what the Eventstream statement of round 4 was for, so the author added the Map statement as a precaution of the same kind (it does not forbid the README's example). Grok and Gemini found it supported in round 6, and Gemini and GPT confirmed from the build's source that the Eventstream builder tools only append to a definition in memory.
- Rule 6 and other targets, and the rule for jobs (round 5). Grok found that no phrase covers a GitHub commit or a write through the SQL MCP Server to a database that is neither a tenant nor Azure, and that a job's agent can follow the rule on approval only by making no change, while the README does not say that no typed executor operation changes a tenant. The author declined both: the rule is about the live state of a tenant or of Azure, because that is what the design refuses and escalates; the SQL MCP Server is in no profile and not in the manifest, so a person has to connect it in their own settings; a job's agent makes no write itself (the executor does, by typed operations that it decides), and the sentence that Grok suggested would contradict the design, where the executor deploys to a sandbox workspace. Gemini closed both as justified (J) in round 6.
- `accept_eula` (rounds 1 and 2). The tool is never called and no job variant may list it, but the lock skipped the capture of every variant of the Power BI authoring server because the license is not accepted, so the test of the job variants takes the tool list of the catalog for it and keeps one exception for `accept_eula`. Whether a job variant lists it cannot be settled without the capture; the exception is marked UNVERIFIED in the test.
- `activator_create_trigger` of the RTI server (round 2). It is a write that needs approval in a session; it creates a trigger with an e-mail or Teams alert, which is no schedule, permission, connection or setting. It is in the short list of reviewed exceptions of the check of protected names, with its reason.

## What the author added

- The catalog (`toolchain/catalog.json`), its validator and generator (`scripts/toolchain_catalog.py`), the command `toolchain.py instructions [--check|--write]` and the drift check V14, so that `AGENTS.md` and the server reference cannot be edited by hand.
- The check of protected names (`unflagged_tools`): a tool whose name says that it touches one of the nine areas and is not read-only, or that returns a secret, has to be flagged by name or named in a statement of a change, under an area that each specific word of its name belongs to. 33 tests of the catalog, and 91 mutations of the catalog code, of the command and of the rules that name the tools that are never called, all killed by the tests (the last full run is in the verification log).
- The programs that read the catalog against its pages (`catalog_quotes.py`: the checklist of statements, the quote check, the comparison of the tool lists of the pages and READMEs with the catalog set by set, and the reduction of the pages to text) and the script that reduces a Learn page to text with its date (`learn_extract.py`). The reviewers read `catalog_quotes.py` and the mutations that had been rewritten or added; nobody read `learn_extract.py`.
- The fact list holds 236 claims now, among them 81 that watch the date of a cited page and 16 that hold the tool list of a server and whose patterns name every tool; 34 tests of `ClaimPrecisionTests` remove the text that a claim stands for from its row, negate it or move it to another row, and expect the claim to stop passing (each of the cases of the last rounds was shown to stay green under the pattern that it replaced).
- Four hand-written texts say the same sentence about approval ("Before anything that changes the live state of a tenant or of Azure": rule 6 of `AGENTS.md`, rule 2 of "How to work" in the preamble, step 1 of the router, the section of the README on instructions for agents), and a test holds each of them to it.

## What was not proved

- The catalog is a reading of pages by a model that other models checked. No person who runs Fabric has reviewed it, and no agent has been run with the files.
- The tool lists of the hosted servers and of the servers that the kit does not pin come from pages and READMEs, not from the servers: the lock measured four stdio servers (the Azure server 4.0.0-beta.4, the local Fabric server 1.6.0, the RTI server 0.6.2, the Bicep server 0.48.1) and skipped the local Power BI authoring server because its license was not accepted. A page can omit a tool or name one that a build does not have: the README of the RTI server omits `kusto_show_command` and lists `kusto_get_shots`, which the lock lacks; the Azure Learn page lists namespaces that the locked build does not have, and the other way round.
- The kinds of a server whose list comes from a page are the writer's reading (a tool that deletes or replaces is `destructive` although the page says write). The statements of a change are precautions, and are not complete for a server that is a router or a namespace (the Azure server, the Power BI authoring routers, `kusto_command`): everything else that changes something needs the approval of rule 6. The check of protected names guards names; it is not proof that the flags are complete.
- Whether a job variant of the Power BI authoring server could list `accept_eula` (UNVERIFIED), whether any typed operation of the executor changes a tenant (the executor is not built), and what rule 6 should say about a repository or a database outside a tenant and Azure (declined, see above).
- The pages change without notice, and a later `updated_at` shows as drift only in the weekly check. The claims of the fact list are drift detectors for the sentences that the catalog cites: each pattern is bound to a whole sentence, a row, a list or a bullet, but a page that keeps the matched sentence and disavows it in another place (a section of removed features, a column of a table, a prompt marked as obsolete) is not detected (14 of the 21 mutations of this kind that GPT tried in round 7). Newer upstream versions were found and reported, not adopted: the local Fabric server 1.7.0, the Azure server 4.0.0-beta.5, the Azure skills v1.2.113 and the Fabric CLI 1.9.0. The weekly check also shows some package versions as drift and cannot reach one package index from this machine.
- The spelling of one Fabric IQ address differs between two pages. The verifier of a job is empty on purpose and so does not get the reference pack (a decision for the owner), and the host files let the Azure cost server expose all its tools.
