# Third look at the instruction layer: findings, checks and outcomes

This is the third look at the instruction layer (`AGENTS.md` with the two files that import it, the preamble that every profile loads, the `factory-router` skill and the `factory-standards` skill, with the update report whose summary the files rely on). The first review (three families, 25 findings) is in [instruction-layer-findings.md](instruction-layer-findings.md) and the closure review (19 new findings) in [instruction-layer-closure-findings.md](instruction-layer-closure-findings.md). The author fixed what the closure review found, and three families then read the corrected layer again, each at a slice that it had not had before, so that every family has now read every slice. Each decided the closure findings of its slice that another family had raised, looked for defects in the fixes, and looked for anything new. The brief that they were given is in [the verification material](../../verification/briefs/instruction-layer-third-look-briefs.md), and the replies are kept as the reviewers wrote them, with the agent's own header removed. The snapshot that they read was a copy of the working folder, taken after the fixes of the closure review and after the records of the closure review, of the reference pack and loop 13 of the verification log were written, and before the fixes that this record lists.

The author's reason for leaving `"tools": ["*"]` in the host files, as he gave it to the reviewer (that a host file can only name tools that the kit has measured), was called wrong in a detail: the renderer writes that array for every server of Copilot CLI, measured or not (eight times in the file), and the VS Code file has no `tools` array. Leaving it is still right, because an entry without the array is listed with `*` and so fails open, which is why a renderer must write one, and the text now says to treat the endpoint as the whole server. A renderer could write an explicit list for this server from the upstream page, and the kit has no field for it. That would limit the server to the cost tools in Copilot CLI only, and it is left to the owner as a hardening.

The weakness that the three findings share cannot be removed by more words in the tests: whatever words a test holds, a clause can be added after them. The author made it structural. `ReviewedTextTests` holds the text of `AGENTS.md`, the preamble, the two skills of this repository, the four reference files and the section of the README on instructions for agents by a digest (of the text with LF endings, so that it is the same on every system). A change to any of them fails the test and prints the new digest, and rule 9 of `AGENTS.md` says what has to happen before the digest is replaced: a model family other than the one that wrote the change checks it, and the result is recorded under `docs/reviews`. The class is not part of the sets of mutations that prove the other tests, because it would kill every one of them and hide what they hold. The 11 mutations of the reviewer that survived, and one of the author's for a line added to the preamble and one for a check of the reference pack, are the set `fourth-look` (f01 to f13): all 13 are killed, 12 by the digests and the one in the code by the new test of the summary.

## What was not proved

- No host was run against a model with these files, and the verifier of a job still does not get the standards pack: both are as in the records before this one.
- The host files list every tool of the Azure Resource Manager server, and nothing limits it to the cost tools. The kit has no field for an allow-list, and the lock has no contract for a server that needs a sign-in.
- The digests make a change deliberate. They do not make a sentence right: that was the work of the four looks, and each found something that the one before it had passed.
- The policy engine that the design uses to refuse the changes of tier T3 is not built, so until it is, the instruction to the agent is the only thing that keeps a job from putting a refused change into its draft.
